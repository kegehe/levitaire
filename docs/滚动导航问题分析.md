# 滚动导航（通用工具 › 滚动导航）失效问题分析

> 分析日期：2026-09-12　范围：`src/tools/scroll-navigator/`、`src/tools/utility-hub/`、
> `src-tauri/src/scroll_navigation.rs`、`src-tauri/src/commands/tools.rs`、`src-tauri/src/hooks/mouse.rs`
> 结论均带实测数据，测量脚本与原始输出见文末「附录」。

## 一、结论摘要

用户反馈的两个症状，对应三处彼此独立的缺陷：

| 症状 | 根因 |
| --- | --- |
| 很多可滑动窗口「无法进行点击」 | **R1** `precise` 门控过严：UIA `ScrollPattern` 只对经典 Win32 滚动控件有效，浏览器 / Electron / 资源管理器 / UWP 一律拿不到 → 百分比输入框、滑杆、5 个预设**永久 disabled**（`opacity:.45`） |
| 点击后界面发僵、点了没反应 | **R2** `get_scroll_navigation_state` 是**同步命令**（跑在 UI 主线程），而前端**每 1200ms 无上限地**做一次深度优先 UIA 跨进程遍历（实测最深 1513 节点 / ~800ms）；窗口隐藏后**照样继续轮询** |
| 有些窗口能点但「点击之后无法生效」 | **R3** 目标窗口只在开启时抓一次且会误抓/失效后永久禁用；**R4** 键盘兜底对所有应用一律用 Ctrl+Home/Ctrl+End，且依赖 `SetForegroundWindow` 抢焦点，忽略按键的应用（资源管理器 / 阅读器 / UWP / 游戏）无任何兜底 |

一句话：**「精确通道」在用户真正会滚的那些窗口上根本不成立，而它被当成了「能不能用」的总开关；同时它的探测本身在拖死整个应用的主线程。**

## 二、实测证据

复刻 `find_scroll_pattern`（ControlView 深度优先、深度上限 14、找 `VerticallyScrollable` 的
`ScrollPattern`），对本机所有可见顶层窗口实测：

| 窗口 | UIA 结果 | 遍历节点 | 遍历耗时 | 备注 |
| --- | --- | --- | --- | --- |
| notepad.exe（长文本） | **FOUND @d3** | 3 | 27ms | `Pane`，`vscroll=True`，`SetScrollPercent(-1,50)` → 50% **生效** |
| WorkBuddy.exe（Electron） | MISS | 1513 | **~800ms** | 仅 `d1 Document` 带 pattern 但 `vscroll=False` |
| chrome.exe | MISS | 163 | ~100ms | **树里没有任何 ScrollPattern**；RawView depth≤4 只有 14 个节点 |
| milevia-desktop.exe（Electron） | MISS | 52 | ~70ms | `d12 Document`，`vscroll=False`，`pct=-1.0` |
| explorer.exe（桌面） | MISS | 109 | ~55ms | 无任何 ScrollPattern |
| GameViewer.exe | MISS | 71 | ~22ms | 无任何 ScrollPattern |
| SystemSettings / Todo / TextInputHost / milevia-siw | MISS | 1 | 1~4ms | 无任何 ScrollPattern |

两条关键推论：

1. **「精确」只覆盖经典 Win32 滚动控件。** Chromium 不实现 UIA `IScrollProvider`，Electron 只把
   `Document` 暴露成 `VerticallyScrollable=False`，资源管理器/桌面/UWP/游戏连 pattern 都没有。
   用户日常会滚的窗口（浏览器、VS Code/Cursor、资源管理器）恰好全在不覆盖的那一侧。
2. **探测成本随目标窗口复杂度爆炸。** 找不到 pattern 就必须走满整棵 14 层子树：Electron 类窗口
   实测 ~800ms。补充实测：把 `vscroll=False` 的 pattern 也拿来调 `SetScrollPercent`，抛
   `0x80131509 COR_E_INVALIDOPERATION`——说明**不是门控写错了，而是树里确实没有可用的滚动器**，
   所以「放宽条件」这条路走不通，必须新增别的通道。

## 三、逐条根因

### R1　`precise` 被当成总开关（“无法进行点击”）

`ScrollNavigator.tsx`：

- 4 个端点按钮：`disabled={!state.fallbackAvailable || busy}`（有目标就可用）
- 百分比输入框 / 滑杆 / 5 个预设：`disabled={!state.precise || busy}`

`scroll_navigation.rs::precise_state()` 只在 `CurrentVerticalScrollPercent()` 返回有效值时才
`precise: true`。结合上表，本机 `precise` **恒为 false** → 中间整块永远 `opacity:.45` + disabled，
用户看到的就是「这些按钮点不动」。现有单测 `ScrollNavigator.test.tsx` 甚至把
「disables percentages」写成了断言，等于把错误假设固化成了规范。

### R2　同步命令 + 无上限轮询把主线程拖死（“点了没反应”）

- wry 在 WebView2 的 `WebMessageReceived` 回调里**内联**调用消息处理（`wry-0.55.1/src/webview2/mod.rs:890`），
  Tauri 的 `ExecutionContext::Blocking` 同步命令因此**直接在事件循环主线程上执行**
  （`tauri-macros-2.6.6/src/command/wrapper.rs:251`）。`get_scroll_navigation_state`、
  `set_scroll_navigation_percent`、`navigate_scroll` 三个都是同步命令。
- 这三条链路里都含 `with_scroll_pattern` → `find_scroll_pattern`：**跨进程 COM，无节点预算、无超时**。
- 前端 `useEffect` 每 **1200ms** 无条件调一次 `get_scroll_navigation_state`。
- 命中 Electron/深树目标时 = 主线程每 1.2s 被占用约 0.8s → 整个应用（悬浮球、面板、所有窗口）
  画面与点击都卡住，表现为「点击无效」。
- 更糟的是：`hide_utility_hub` 只是 `window.hide()`，窗口对象与 React 树都还在，
  `mode==="scroll"` 时 `ScrollNavigator` **保持挂载** → 全仓库没有任何 `visibilitychange` 处理
  （已 grep 确认）→ **面板已经关掉、看不见了，UIA 轮询还在继续**。

### R3　目标窗口的抓取策略（“能点但没效果”）

`TARGET_HWND` 只在三处写入：

1. `start_utility_hub` / `start_scroll_navigation` / `show_palette` 里的 `capture_current_target`：
   hide palette → 轮询 `GetForegroundWindow()` 12 次 ×10ms，**要求是非 Levitaire 窗口**，
   否则回落到 `LAST_EXTERNAL_TARGET`。
2. 鼠标钩子的 `remember_foreground_snapshot`：**任何**鼠标按下时若前台不是 Levitaire 窗口，
   就把该窗口写成目标。

由此产生四类错配：

- **不跟随。** 轮询里没有「重新采样目标」，只认开启那一刻的窗口。先开面板再切到别的 App，
  后面所有操作仍发给旧窗口 → 在新窗口上点按钮「没反应」（其实是滚了背后的旧窗口）。
- **单点跟随失效。** 钩子取的是**点击前**的前台窗口，所以「点目标 App」这一步不会把目标切过去；
  必须再回到导航面板上点一下才重定目标（这个副作用反而成了事实上的跟随机制，很脆）。
- **误重定。** 只要按下瞬间前台不是 Levitaire，就会写目标。面板失焦后（例如刚做过一次键盘兜底，
  目标 App 已置前）在面板上点按钮，会把「刚好在前台的那个 App」写成目标。
- **一旦目标窗口关闭，`target_window()` 返回 None → `fallbackAvailable=false` → 4 个按钮也一起永久
  disabled**，只能关掉重开面板才能恢复。

### R4　键盘兜底本身不可靠

`send_navigation_keys`：

- `top`/`bottom` 对**所有**应用一律发 `Ctrl+Home` / `Ctrl+End`（注释里只为终端考虑）。资源管理器、
  图片/PDF 阅读器、UWP 里这些组合键无效或语义不同。
- 依赖 `activate_target`（`AttachThreadInput` + `SetForegroundWindow`）抢前台；失败即
  「无法激活目标窗口」。抢到前台会**把焦点从导航面板夺走**，此后用户每次点面板都要多花一次
  点击/一次激活，观感更差。
- 对忽略按键的应用（游戏、部分 UWP、带自绘滚动的阅读器）**没有任何兜底**——没有
  `WM_MOUSEWHEEL` / `WM_VSCROLL` / `SetScrollPos` 通道。
- 目标恰好是桌面（`Progman`/`WorkerW`）时按钮是启用的，但按什么都没用——用户视角就是
  「能点，点了没效果」。

## 四、建议修复（按优先级）

**P0　先把主线程救出来（低风险，立刻改善“点不动”）**

1. `get_scroll_navigation_state` / `set_scroll_navigation_percent` / `navigate_scroll` 改为 `async`
   或 `tauri::async_runtime::spawn_blocking`，把 UIA 调用整体移出主线程。
2. 加缓存：以「目标 HWND + 时间戳」为键做 ~500ms TTL 的 `ScrollNavigationState` 缓存，
   轮询间隔放宽到 2s，目标没变就直接返回缓存。
3. 面板隐藏 / 失焦时**停止轮询**（前端 `visibilitychange`，或 hide 时后端发事件暂停）。
4. `find_scroll_pattern` 加节点预算（例如 800 节点 / 150ms）与提前放弃，杜绝深树拖死。

**P1　让「精确」真正覆盖日常窗口**

5. 精确通道改成降级链：`UIA ScrollPattern` → Win32 `GetScrollInfo`/`SetScrollPos(SB_VSCROLL)` →
   **`WM_MOUSEWHEEL` 注入**（对 Chromium / Electron 最普适，可先 `SetCursorPos` 到目标窗口中心再
   发滚轮）。UIA 只作为「能拿到百分比就直接用」的加速项，不再作为唯一通道。
6. 前端诚实降级：`precise=false` 时**不要整块 disabled**。把「−10% / +10% / 翻页」这类永远可用的
   步进控件作为主控件，百分比输入与预设仅在 `precise` 时出现（或降级为只读显示）。

**P2　目标窗口策略**

7. 每次操作前用「最后一次非 Levitaire 前台窗口」重新确认目标；在鼠标钩子里对**点击落在该窗口矩形内**
   的非 Levitaire 前台窗口更新目标（修掉 R3 的误重定与不跟随）。
8. 目标失效不要永久禁用：实时重新捕获，并在 UI 上给「目标窗口已关闭，点击重新选择」的入口。

**P3　键盘兜底**

9. `top`/`bottom` 去掉 `Ctrl`（仅终端/控制台保留），或「先 Ctrl+Home/End，失败再 Home/End」。
10. 补 `WM_MOUSEWHEEL` / `WM_VSCROLL` 兜底；`activate_target` 失败时用
    `AllowSetForegroundWindow` 或模拟 Alt 键提升置前成功率。

## 五、修复实现（2026-09-12 已完成）

### 1. 通道从「UIA 单通道」改成三级降级（R1 / R4）

`scroll_navigation.rs` 重写为三条通道，按可靠性降级：

| 通道 | 实现 | 覆盖 |
| --- | --- | --- |
| 精确 | UIA `ScrollPattern`（探针带节点/时间预算） | 经典 Win32 滚动控件 |
| 键盘 | `PostMessage` `Ctrl+Home`/`Ctrl+End`/`PgUp`/`PgDn` | 浏览器、Electron |
| 滚轮 | `PostMessage` `WM_MOUSEWHEEL`（取窗口中心为坐标） | 通用（含资源管理器、阅读器） |

关键点：**全部走 `PostMessage`，不再 `SetForegroundWindow` + `SendInput`** ——
实测投递的消息不需要抢前台，所以导航面板不再因为一次滚动就丢掉焦点。

到顶/到底 = 精确 → 按键 → 滚轮长推（800 格）。两路都是「幂等收敛到边缘」的动作：
按键生效时滚轮只是把已在边缘的窗口继续同向推（被夹住），按键被忽略时滚轮才真正起作用。

前端：`precise=false` 时**不再整块 disabled**，中间区换成「相对滚动」（上/下滚 3 格，
走滚轮通道）；端点按钮与微调只依赖「存在目标窗口」。

### 2. 线程与轮询（R2）

- `get_scroll_navigation_state` / `set_scroll_navigation_percent` / `navigate_scroll` /
  `start_utility_hub` / `start_scroll_navigation` / `recapture_scroll_target` 全部改
  `async` + `tokio::task::spawn_blocking`，跨进程 COM 彻底离开事件循环主线程。
- `find_scroll_pattern` 加 **600 节点 / 120ms** 双预算（原先无上限）。
- 探测结果按「目标 HWND + 800ms TTL」缓存，前端轮询 1200ms → **2000ms**，
  且 `document.hidden` 时停止轮询（面板只是 `hide()`，React 树不卸载；已确认
  `Window::set_visible` 会走到 WebView2 `SetIsVisible`，所以隐藏时确实会触发
  `visibilitychange`）。
- COM 从 STA 改为 **MTA**：UIA 客户端跑在没有消息泵的阻塞线程池上时，STA 有死锁风险。

### 3. 目标窗口（R3）

- 目标改按**点击落点**判定：`GetAncestor(WindowFromPoint(x, y), GA_ROOT)` 才是用户点中的窗口。
  **不能用前台窗口**：低层鼠标钩子在消息投递到目标窗口之前就被调用，此时
  `GetForegroundWindow()` 返回的还是点击前那个窗口 —— 用它会同时造成「点进新程序切不过去」
  与「在面板上点按钮时把碰巧在前台的程序误记成目标」。落点求窗口两个问题一起消失。
- 「点在自己身上」（悬浮球 / 面板按钮）时不更换目标，只把**点击前的前台窗口**记为候选
  （`LAST_EXTERNAL_TARGET`）—— 用户点悬浮球之前正在用的程序才是最可能想滚的对象。
- 目标窗口失效时回退到该候选（不再永久禁用）；新增命令 `recapture_scroll_target` +
  面板上的「重新选择目标」按钮：收起自己 → 抓前台 → 再显示回来，一键重绑。

### 4. 新增/更新的守卫

- Rust：`wheel_wparam` / `wheel_lparam` 位打包、消息号与 `WHEEL_DELTA`、
  `action_plan_keeps_the_two_direction_conventions_aligned`（UIA 百分比 0=顶部 与
  滚轮正=向上 是两套反向约定，写反不会编译失败）、扫描预算。
- 前端：`ScrollNavigator.test.tsx` 覆盖「无精确滚动条时相对区仍可用」与
  「无目标时给一键重绑」——旧版把「disables percentages」写成断言，等于把错误假设固化了。

### 5. 实测回归（本次新增）

`D:\tmp\scroll-nav-audit\edge_probe.py`（Chromium，约 6 万像素长页）：

| 动作 | 结果 |
| --- | --- |
| 投递滚轮下推 800 格 ×2 | 第二次快照与第一次**完全一致** → 已夹在底部（第一次即到底） |
| 投递滚轮上推 800 格 ×2 | 回到页面顶部基线，再推一次不变 → 已夹在顶部 |
| 投递 `Ctrl+Home` | 精确回到顶部基线 |
| 投递 `Ctrl+End` | 精确到达底部（与滚轮到底的快照一致） |
| 以上全部 | **不抢前台、不移动光标**（面板不失焦） |

另外 `wheel_probe.py` 早期已验证：`PostMessage(WM_MOUSEWHEEL)` 与无修饰的
`WM_KEYDOWN VK_NEXT` 在 Chromium 上都生效，且带/不带激活结果一致。

## 六、二次复查（对本次改动逐行自查）发现并修掉的问题

### 1. 滚轮投递目标错了（功能性 bug，必须改）

原实现把 `WM_MOUSEWHEEL` 投给**目标顶层窗口**。实测资源管理器（`CabinetWClass`）的可滚动
列表是子窗口 `DirectUIHWND`：

| 投递目标 | 结果 |
| --- | --- |
| 顶层 HWND | **完全不滚动**（快照无变化） |
| 落点子 HWND | 滚动（快照变化），继续下推、上推复位都正常 |

而资源管理器恰好**没有 UIA 滚动器、也不理会投递的按键**——滚轮是它唯一的通道，所以这条错了
等于资源管理器依旧「点了没反应」。系统本来就是按「光标下的窗口」投递 `WM_MOUSEWHEEL` 的，
这里只是复刻它。已改为投「落点处的子窗口」，并加两条护栏：落点被**我们自己的置顶浮窗**盖住、
或落点属于**别的进程** → 退回顶层窗口。

回归验证：Chromium（`Chrome_RenderWidgetHostHWND`）投子窗口同样有效，上推 60 格能精确回到
基线快照；投顶层也有效（两种都行，取更忠实的子窗口）。

### 2. 桌面 / 任务栏会变成「粘住的死目标」

`WindowFromPoint` 落在桌面时，旧逻辑会把 `Progman` 记成滚动目标 → 面板停在
「按钮都可用、但点了完全没反应」，而且这个目标是持久的：用户随手点一下桌面（用来收起面板之类）
就会踩到。已加 `is_shell_window`（`Progman` / `WorkerW` / `Shell_TrayWnd` /
`Shell_SecondaryTrayWnd`）过滤，三处入口（开启时抓取 / 鼠标点击 / 取用时校验）统一走
`is_usable_target`。现在这种情况会诚实地变成「未绑定目标 + 重新选择目标」。

### 3. 设置失败后的回读被 busy 守卫吞掉（前端）

`setPercent` 的 catch 里 `await refresh()` —— 但 `refresh()` 开头就是
`if (busyRef.current) return;`，而此时 `busy` 还没解除，**回读永远不执行**，UI 停在过期数值上。
已抽出不带守卫的 `fetchState()` 供其复用，并加了回归测试（断言失败后回读到真值而不是停在
点击时的值）。

### 4. 其它

- 微调按钮写「上滚 3 行」，实际是 3 个**滚轮格**（Chrome 约 300px），已改为「3 格」（含测试
  与文档同步）。
- `recapture_scroll_target` 原先在 async 上下文里调 `is_visible()`——它是「发消息给事件循环并
  等回执」的**阻塞** getter，已移进阻塞任务执行（`show` / `hide` / `set_focus` 是
  fire-and-forget，不受影响）。
- 顺带确认（非缺陷）：`send_user_message` 有主线程快路径，同步命令在主线程调窗口 getter
  不会死锁——旧代码里 `is_visible()` 本身是安全的，问题只在于它同时把 UIA 也放在了主线程。

### 第二轮复查（再走一遍集成面）

1. **async 体里还剩两处阻塞调用**：`start_scroll_navigation` 与 `recapture_scroll_target` 结尾
   直接调 `crate::scroll_navigation::state()`——那是一次跨进程 UIA 遍历（最坏 ~120ms），
   放在 async 上下文等于把刚搬走的阻塞又搬回了一个 worker 线程。已改为**在阻塞任务里顺带把
   状态算出来返回**，两个 async 函数体现在只剩窗口 show/hide（fire-and-forget）与结果组装。
2. **通用工具里的紧凑尺度没同步给新控件**：`UtilityHub.css` 对每个 `.scroll-nav-*` 都有一份
   紧凑覆盖（端点按钮 23px、预设 20px/9px、百分比 17px），因为面板只有 216px 宽、而
   `ScrollNavigator.css` 那套是给独立窗口（248px）写的。我新增的 4 个控件漏了覆盖 →
   上/下滚按钮会是 26px、错误行是 11px，在这个面板里明显偏大。已补 `.scroll-nav-hint` /
   `.scroll-nav-steps button` / `.scroll-nav-recover button` / `.scroll-nav-error` 四条覆盖，

### 已知取舍（有意保留）- `到顶/到底` 在非精确窗口上会补一次 **800 格滚轮长推**。对浏览器这类「按键已生效」的窗口，
  页面已在边缘，这 800 条消息不会产生位移（不会重复触发滚动事件）；对忽略按键的窗口，
  它才是真正起作用的通道。副作用是：极少数「滚轮不是滚动」的程序（看图、地图类）会跟着动，
  这与「到顶/到底」的语义本就无意义。
- 目标进程若以更高完整性级别运行（管理员窗口），`PostMessage` 会被 UIPI 拦掉——这与旧的
  `SendInput` 路径的限制相同，不是回归。
