# 长截图实现方案

> 调研日期：2026-08-24  
> 适用版本：Levitaire 0.1.x  
> 目标：在现有 Windows 截图工具中增加可靠的纵向滚动长截图能力

---

## 一、结论摘要

长截图不应被实现为“把普通截图的 Canvas 拉长”。当前截图工具是一次性 GDI 截屏，普通截图完成后由前端 Canvas 标注并导出。滚动长截图需要在用户滚动期间连续抓取多个可见区域，再进行重叠检测、去重和拼接。

推荐采用分阶段、可扩展的混合架构：

1. 第一版：手动纵向滚动 + Rust 分段抓取 + Rust 图像拼接。
2. 第二版：在同一会话接口上增加 UI Automation 自动滚动。
3. 后续：针对 Chrome/Edge 增加浏览器专用路径，并保留手动拼接作为通用回退。

第一版不应该承诺所有应用都能自动滚动到底。Windows 没有对任意窗口都可靠的“获取完整滚动内容”通用接口。

## 二、当前截图链路

### 2.1 前端入口和状态

主要代码位于 `src/tools/screenshot/ScreenshotTool.tsx`：

- `Mode` 当前只有 `selecting` 和 `annotating`。
- `SelectMode` 当前只有 `region` 和 `window`。
- `onPointerUp` 把 CSS 坐标换算成虚拟桌面物理坐标，然后调用 `capture_region`。
- `capture_region` 成功后，结果进入 `CapturedImage`，随后交给 `AnnotationCanvas`。
- 保存、复制、OCR、钉图均依赖当前 `image` 和 `selection`。

标注画布在 `src/tools/screenshot/annotate/AnnotationCanvas.tsx` 中按原图宽高创建 Canvas，并从 `data:image/png;base64,...` 加载图片。

### 2.2 后端截图链路

`src-tauri/src/commands/mod.rs` 的 `start_screenshot_inner` 会：

1. 检查截图会话和录制会话状态。
2. 隐藏悬浮球、工具栏和其他浮动 UI。
3. 等待 DWM 合成一帧。
4. 使用 `capture_screen_region` 抓取完整虚拟桌面。
5. 将 BGRA 像素放入 `ScreenCache`。
6. 显示覆盖层窗口，等待前端框选。

`capture_region` 主要做缓存裁剪和 PNG base64 编码，而不是重新抓屏。

### 2.3 现有约束

`src-tauri/src/screenshot/mod.rs` 中当前有以下限制：

- 单边最大 32768 像素。
- 总像素上限 100,000,000。
- BGRA 原始数据最高约 381 MiB，编码和前端传输还会产生额外副本。

`src-tauri/src/hooks/mouse.rs` 已增加 `WM_MOUSEWHEEL` 转发。钩子本身不执行抓屏或拼接，只将滚轮坐标和方向交给长截图 worker；当前实现只处理向下滚动，并校验事件点是否属于启动时记录的目标窗口根窗口，因此拖动选区外滚动条也能触发采样，同时不会响应其他应用的滚轮。

## 三、方案比较

| 方案 | 适用范围 | 优点 | 主要问题 | 结论 |
|---|---|---|---|---|
| 手动滚动 + 图像拼接 | 任意 Windows 应用 | 兼容性最高，用户可控制结束时机 | 需要用户慢速滚动，动态内容可能影响匹配 | 第一版采用 |
| `SendInput` 模拟滚轮 | 普通桌面应用 | 可以自动化滚动 | 依赖焦点，受 UIPI/管理员权限影响，应用行为不统一 | 后续增强 |
| UI Automation `IScrollProvider` | 支持 UIA 的应用 | 可读取滚动状态，能判断到达底部 | 浏览器、远程桌面、自绘控件兼容性不稳定 | 后续增强 |
| 浏览器 DOM/CDP 截图 | Chrome/Edge 页面 | 可直接获得页面内容，拼接质量最好 | 不能覆盖任意桌面窗口，需要浏览器专用集成 | 后续增强 |
| `PrintWindow` / `BitBlt` 一次抓取 | 当前可见窗口 | 实现简单 | 不能可靠获取视口外的滚动内容 | 不采用 |

参考实现：

- [eSearch 滚动截屏说明](https://github.com/xushengfeng/eSearch/blob/master/docs/use/long_clip.md)：手动慢速滚动、实时预览、显式结束。
- [ShareX ScrollingCaptureService](https://github.com/ShareX/ShareX/blob/develop/ShareX.ScreenCaptureLib/ScrollingCaptureService.cs)：延迟抓帧、边缘忽略、图像匹配、部分成功状态。

## 四、第一版用户流程

1. 进入截图模式，选择“长截图”。
2. 用户框选需要滚动的视口区域。
3. 后端记录物理坐标和截图会话代次；目标窗口优先通过选区中心点探测，无法确认时回退到进入截图前的前台窗口。
4. 隐藏全屏截图覆盖层，同时保持悬浮球、工具栏等 Levitaire 窗口隐藏，避免它们重新暴露后被抓入图片。
5. 恢复目标窗口前台状态；目标窗口无法激活时，用户可以手动点击后继续。
6. 显示鼠标穿透的固定采集区域边框和不抢焦点的控制栏。两者在采样时临时隐藏，避免进入图片。
7. 后端先抓取一帧作为初始结果，确认抓帧时目标窗口已经稳定。
8. 用户可在目标窗口正常点击、输入、拖动滚动条或向下慢速滚动；采集区域的屏幕坐标保持不变。
9. 滚轮、滚动键或目标窗口内的鼠标释放会触发等待；约 250ms 后抓取固定区域的一帧并拼接。
10. 控制栏显示帧数、当前高度和匹配状态。
11. 用户点击“完成”后，进入预览和保存状态。

Esc 取消当前长截图，取消后必须丢弃未完成结果；“完成”后的结果不能因为截图 overlay 关闭而被清除。

“完成”操作必须先停止接收新的滚轮事件，再等待 worker 处理完最后一次延迟采样，最后原子地把结果状态切换为 `Completed`。不能让控制栏点击和最后一帧拼接并发修改同一个结果。

## 五、推荐技术架构

### 5.1 新增 Rust 模块

建议新增：

```text
src-tauri/src/scroll_capture/mod.rs
```

该模块负责会话、滚轮事件、抓帧、拼接、结果缓存和状态事件。不要把拼接算法继续堆入 `commands/`。

核心状态可以设计为：

```text
LongCaptureSession
  region: CaptureRegion
  target_hwnd: HWND 或窗口标识
  previous_frame: BGRA
  stitched_bgra: BGRA
  width: u32
  height: u32
  frame_count: u32
  status: Capturing / Partial / Completed / Cancelled
  generation: u64
  result_id: u64
```

只保留上一帧和最终结果，不保留所有历史帧。这样内存主要与最终图片大小相关。

### 5.2 建议命令

```text
start_long_capture(left, top, width, height) -> resultId
stop_long_capture(resultId) -> LongCaptureSummary
cancel_long_capture(resultId)
get_long_capture_status(resultId)
get_long_capture_preview(resultId)
save_long_capture(resultId)
clipboard_set_long_capture(resultId)
```

完整结果应保存在 Rust 状态中。所有读写结果的命令都必须带 `resultId`，避免旧会话的异步回调操作新会话结果。`get_long_capture_preview` 只返回缩略图，避免把几十 MB 的 PNG base64 传到 React。

### 5.3 鼠标钩子

在 `hooks/mouse.rs` 中新增 `WM_MOUSEWHEEL` 分支：

- 读取滚轮方向和鼠标坐标。
- 只在长截图会话激活时转发事件。
- 只接受落在采集区域内或目标窗口根窗口内的滚轮事件。
- 不在 `WH_MOUSE_LL` 回调中执行 GDI 抓屏或图像拼接。
- 将事件发送到独立的长截图 worker。

长截图 worker 负责节流和延迟抓帧，避免滚轮动画尚未结束就采样。

### 5.4 控制栏

录屏已经有独立 `recording-controls` 窗口。长截图可以：

- 复用该窗口并增加模式；或
- 新增 `long-capture-controls` 窗口，减少录屏状态耦合。

控制栏必须位于截图区域之外，且不能被后续抓帧截入。全屏 overlay 在采样期间应隐藏或点击穿透。隐藏 overlay 后不能依赖普通截图阶段恢复浮动 UI 的逻辑，长截图会话需要单独保证 orb、toolbar、palette 等窗口持续隐藏，并在结束时按会话前状态恢复。

## 六、图像拼接算法

对于向下滚动，新帧顶部通常与上一帧中间区域重叠：

```text
上一帧：  [旧内容.........................]
新一帧：          [重叠.........][新增内容]
```

每次拼接建议：

1. 忽略左右 5%～10% 的区域，避免滚动条和固定侧栏干扰。
2. 在上一帧尾部和当前帧头部之间搜索候选重叠高度。
3. 使用采样行或像素块计算相似度，避免逐像素全图比较。
4. 要求连续多行匹配，防止重复文字或纯色区域误匹配。
5. 只追加当前帧未重叠部分。
6. 匹配失败时保留已有结果，并标记为“部分成功”，不能盲目追加整帧。

固定表头和固定底栏不能只靠左右边缘忽略解决。建议在前 2～3 帧中计算每一行的稳定性：连续多帧在相同位置保持不变、且位于视口顶部或底部的行，标记为固定区域；匹配和追加时排除该区域。无法可靠识别时不要声称“已自动去除”，应显示部分成功状态并允许用户结束。

需要处理的特殊情况：

- 滚动距离小于一行，可能产生高比例重叠。
- 滚动动画未结束，前后帧存在局部模糊。
- 固定表头或固定底栏在每一帧重复出现。
- 页面动态刷新导致相同位置像素变化。
- 用户向上滚动，方向和拼接模型不一致。
- 到达底部后重复抓到同一帧。

第一版建议只支持向下滚动。检测到向上滚动或连续两次无有效位移时，提示用户完成或继续调整，不自动拼接错误内容。

## 七、内存和导出策略

### 7.1 建议限制

第一版必须增加独立的长图限制，不直接沿用普通截图的 100MP 上限：

- 默认警告：超过 20MP。
- 硬限制：初始建议 30MP，具体值通过实机内存测试确定；不能把“30～50MP”直接作为不变的产品承诺。
- 单边仍限制在 Windows/GDI 和编码器可接受范围内。
- 复制需要比保存更严格的独立上限，因为 CF_DIB 是未压缩像素，可能瞬间占用数百 MiB。

Rust 侧应使用 `MAX_LONG_CAPTURE_PIXELS`，所有宽高相乘和结果高度累加都使用 checked arithmetic。普通截图的 `MAX_SCREENSHOT_PIXELS` 不应被隐式复用为长图上限。

最终 PNG 编码、文件写入和大图复制都应放入 `spawn_blocking` 或独立线程，不能阻塞 Tauri 命令线程、滚轮 worker 或窗口消息循环。

例如 1440×20000 的 BGRA 原图约 110 MiB，PNG 编码、缩略图和复制过程还会产生临时副本。

### 7.2 功能支持范围

第一版建议：

| 功能 | 第一版策略 |
|---|---|
| 保存 PNG | 支持，Rust 直接编码和写文件 |
| 复制图片 | 支持，但设置尺寸或内存保护 |
| 实时预览 | 支持缩略图，不传完整原图 |
| 标注 | 暂不复用现有 Canvas |
| OCR | 暂不支持，后续分块 OCR |
| 钉图 | 暂不支持，或只允许缩放后的预览图 |

现有 `save_image`、`clipboard_set_image` 和 `pin_image` 都以 base64 PNG 为输入，不能直接用于无上限长图。新增保存命令应继续遵循当前截图保存目录配置和系统保存对话框回退逻辑；复制应使用独立的尺寸阈值和 BGRA/DIB 直通接口；钉图默认禁用，避免创建超大原生窗口。

## 八、前端改造边界

建议不要强行让长图复用普通 `AnnotationToolbar`。普通截图和长截图应有不同的结果状态：

```text
NormalImageResult
  base64 / width / height / selection / annotations

LongImageResult
  resultId / width / height / frameCount / status / previewBase64
```

前端长截图状态至少包括：

```text
selecting
capturing
stitching
previewing
saving
cancelled
error
```

长图预览使用 `<img>` 或分块预览组件，不创建原始尺寸 Canvas。后续如果需要标注，应采用缩放预览、归一化坐标和 Rust 导出时烧录的方案。

---

## 九、会话和清理要求

长截图必须接入当前截图会话的代际机制：

- `cancel_screenshot` 和全局 Esc 都能取消长截图。
- 旧 worker 不能在新会话开始后继续写结果。
- `cleanup_screenshot_session_inner` 必须停止长截图 worker。
- 取消时释放上一帧、最终 BGRA 和预览缓存。
- 活跃采集会话和已完成结果必须分离：清理 overlay 时停止活跃 worker，但不能自动删除带 `resultId` 的已完成结果。
- 完成后的结果应独立于 overlay 生命周期保留，直到保存、复制或用户明确关闭。
- 启动录屏前必须取消长截图，避免两个采集器同时运行。

普通截图使用的 CSS 坐标到物理坐标换算仍然适用于长截图选区。长截图内部只保存虚拟桌面物理坐标；前端预览缩放不能反向修改采集区域，避免 125%/150% DPI 下出现累计误差。

## 十、后续自动化路线

### 10.1 UI Automation

尝试获取目标窗口的滚动容器和 `IScrollProvider`，读取当前位置和最大位置。支持时可以自动滚动并准确判断到底。

兼容性不足时必须回退，不应因为 UIA 查询失败而结束整个截图流程。

### 10.2 模拟滚轮

使用 `SendInput` 或目标窗口消息模拟滚动。需要处理：

- 目标窗口焦点恢复。
- 目标窗口被关闭、移动或改变尺寸时的会话失败处理。
- 管理员窗口的 UIPI 限制。
- 浏览器平滑滚动动画。
- 远程桌面和游戏类窗口的特殊输入处理。

### 10.3 浏览器专用路径

如果未来需要高质量网页长截图，可以增加浏览器扩展或调试协议通道，直接读取 DOM 页面尺寸并截图。该路径不应污染通用桌面截图流程。

## 十一、测试计划

### 11.1 Rust 单元测试

- 两帧存在明确重叠时的拼接高度。
- 无重叠时返回部分成功或错误。
- 重复帧不会无限增长。
- 固定顶部/底部行的识别和排除。
- 小滚动距离和大滚动距离。
- 固定侧栏被忽略时仍可匹配。
- 超过像素和高度限制时拒绝。
- 取消后旧 generation 不能更新结果。
- BGRA 拼接结果的宽高和行顺序正确。

### 11.2 前端测试

- 长截图模式能传递正确的物理坐标。
- 开始、滚动状态、完成、取消和错误事件能正确切换 UI。
- 保存期间失焦不会误取消。
- 取消后旧预览不会复活。
- 长图预览不会创建原始尺寸 Canvas。

### 11.3 手工验收矩阵

- Chrome/Edge 长网页。
- Notepad、VS Code、PDF 阅读器。
- 固定表头和动态内容页面。
- 125%/150% DPI。
- 多显示器和负虚拟桌面坐标。
- 无滚动内容的普通窗口。
- 管理员权限窗口。
- 远程桌面环境。
- 20～30MP 长图的保存、复制、取消和内存占用，并验证超过硬限制时的拒绝行为。
- 目标窗口失焦、移动、关闭以及无法重新激活的情况。

## 十三、验收标准

第一版完成的最低标准：

- Chrome/Edge、Notepad、VS Code 至少各有一个可用案例。
- 用户慢速向下滚动时，连续 5 帧以上能够正确去重拼接。
- 固定表头经过稳定性检测后不会重复出现在最终图片中；无法判断时必须明确标记为部分成功。
- Esc 和取消按钮都能可靠终止采集并释放内存。
- 结果保存不依赖完整图片通过前端 base64 传输。
- 普通截图、录屏和截图 OCR 现有流程不回归。

### 第一版实际边界（与实现同步）

- 第一版仅支持手动向下滚动和通用屏幕采样；不实现自动滚动、UI Automation、浏览器 DOM/CDP 或固定表头/底栏自动去重。
- 固定表头、固定底栏和动态刷新内容可能被重复拼接。检测失败时只保留已有结果并标记为“部分结果”，不得宣称已自动去重。
- `save_long_capture` 由后端根据保存目录配置或系统对话框生成文件名，当前不接受前端传入 `filename`。
- 长截图复制按解码后的未压缩 DIB 大小限制为 48 MiB，超过限制必须使用保存文件。
