# 系统清理工具实现方案

> 目标：在 Levitaire 中新增一个悬浮工具「系统清理」，能对任意一台 Windows 机器做**深度但绝不破坏系统**的磁盘清理与占用发现。
>
> 本文档是实施规格，不是调研报告。所有结论已合并调研结果与实测数据，逐条给出对策与验证方式。

---

## 一、结论摘要

1. **这个工具的核心矛盾是：可删除的空间有多大，取决于我们敢删多少；而敢删多少，取决于我们能不能证明删了没事。** 因此方案的重心不在"清理算法"，而在**安全机制与可审计性**。
2. **不采用"硬编码规则表 + 自己实现一切删除"的形态。** 规则表必须可外部更新（否则追不上别人电脑上的软件变化），删除逻辑必须尽量复用官方清理器（减少我们自有的破坏性代码）。
3. **分级维度不是"来源"（规则库 / 发现），而是"目标性质"（可再生缓存 / 未知目录 / 用户数据）。** 用户数据永不永久删除。
4. **三道安全闸是地基，必须先写、必须单独验证、必须有蜜罐测试。** 这是唯一能独立证明正确的模块。
5. **输出的核心价值是解释"为什么这些不能动"**，而不是删除量。第三方清理工具的信任危机正来自"只报喜不报忧"。

## 二、设计前提与不变量

以下 12 条是整个功能的**不变量（Invariant）**，任何实现细节不得违反。代码 review 与测试守卫都以这张表为准。

| 编号 | 不变量 | 违反后果 |
|---|---|---|
| **I1** | 前端（WebView）永远不提供路径，只提供 `rule_id` 或后端签发的 `discovery_id`（见 §8.5） | 前端一旦能传路径，等于把删除任意文件的能力暴露给最易被攻破的层 |
| **I2** | 白名单 fail-closed：未在规则表中列举的目标一律不可删 | 黑名单永远不完整，Windows 每次更新都可能新增关键路径 |
| **I3** | 红线前缀**在运行时从环境派生**（`%SystemRoot%` 等），不写字面量；规则表无权覆盖 | 系统盘非 `C:` 时字面量红线全部失效；规则热更新一旦被滥用即可删系统 |
| **I4** | 递归永不跟随重解析点（junction / symlink / mount point） | **调研中破坏性排名第一**：删掉链接指向的真实数据，可能在别的盘或网络位置 |
| **I5** | 占用即跳过：不重试、不强删、不删一半、不自动关进程 | 半毁的目录树比没删更危险；强关进程会丢用户未保存数据 |
| **I6** | 用户数据（文档/下载/桌面/图片/视频/音乐）永不永久删除，只能进隔离区 | 不可逆的数据丢失 |
| **I7** | 提权进程只接受 job id 与 `rule_id`，绝不接受路径参数；**且不把任何非特权方可写的数据作为授权依据** | 否则构成"以管理员身份删除任意文件"的本地提权原语 |
| **I8** | 任何删除动作必须有审计记录（删了什么、跳过什么、为什么） | 失去唯一自证手段；出事无法取证 |
| **I9** | 长任务单飞：同一时刻只允许一个扫描/清理任务 | 两个删除任务并发产生不可预期的中间状态 |
| **I10** | 服务状态（启动类型 + 运行状态）用完必须还原 | 顺手把服务设成 Disabled 属于"修改用户原有配置" |
| **I11** | 提权进程写文件必须防重定向：目标已存在则拒绝（`CREATE_NEW`）+ 拒绝父目录为重解析点 | 符号链接攻击可造成**管理员权限下的任意文件覆写**（§9.1 详述） |
| **I12** | 用户数据目录判定**优先于**规则表判定 | 一条指向 `Documents` 的规则会被误判为"可再生缓存"并永久删除用户文件 |

## 三、威胁模型：会导致系统损坏的路径

调研得到的 12 类陷阱，逐条给出本方案的对策与验证方式。**这张表是安全机制的需求来源。**

| # | 陷阱 | 破坏性 | 本方案对策 | 验证方式 |
|---|---|---|---|---|
| 1 | 递归删除跟随 junction / symlink | 灾难性不可逆数据丢失 | I4：逐层 `GetFileAttributesW` 检查重解析位，遇链接只删链接本身 | **蜜罐测试**（见 §12.2） |
| 2 | 手工删 `WinSxS` | 无法启动 / 无法更新 / 无法修复 | 红线前缀 + 只提供 DISM 方式（L2） | 规则校验器拒绝 |
| 3 | 删 `Windows\Installer` / `ProgramData\Package Cache` | 延迟暴雷：软件无法卸载/修复（1612/1635/1642/1714） | 红线前缀，且**规则表无此项** | 规则校验器拒绝 |
| 4 | 删 `DriverStore\FileRepository` 目录 | 硬件失效，可能断网/无法启动 | 红线前缀；仅 L3 通过 `pnputil` 处理 non-present | 规则校验器拒绝 |
| 5 | 删 `System Volume Information` / `vssadmin delete shadows` | 永久失去回滚网；被 AV 按勒索行为拦截 | 红线前缀；L3 默认折叠 + 输入确认文字 | 规则校验器拒绝 |
| 6 | 路径规范化缺失（`..` / 8.3 短名 / `\\?\` / UNC / `StartsWith` 前缀） | 白名单被绕过 | §6 闸一 | 单元测试全覆盖 |
| 7 | 按文件系统路径直删回收站 | shell 一致性破坏 | 只走 `SHEmptyRecycleBin` / `SHQueryRecycleBin` | 命令守卫测试 |
| 8 | 对占用文件强删 / 删一半 | 目录树半毁、应用数据库损坏 | I5：闸三，占用即跳过并分类统计 | 集成测试 |
| 9 | `DISM /ResetBase` | 永久无法卸载当前已装更新 | L3，默认不暴露，需输入确认文字 | UI 守卫测试 |
| 10 | 禁用保留存储 / 关休眠的连带效应 | 更新失败 `0x80070070`；快速启动失效 | L3，后果文案强制展示 | UI 守卫测试 |
| 11 | `PendingFileRenameOperations` 条目累积 | 下次重启误删健康文件 | **完全不使用该机制** | 源码守卫测试 |
| 12 | 长路径（>260）处理缺失 | 删除静默失败或路径截断误伤 | §7.3 | 单元测试 |

## 五、数据模型：规则表

### 5.1 为什么外部化

规则硬编码在 Rust `const` 中意味着**每调整一条路径都要重新编译、发版、等用户更新**。而 Steam 库路径、Chrome 配置序号、WSL 发行版名、各家 IDE 缓存目录会随版本变化。**靠发版速度追不上别人电脑上的变化**，通用性目标会自我否定。

### 5.2 规则文件格式

随包分发的 `resources/rules/disk-cleanup.json`，可热更新：

```json
{
  "schemaVersion": 1,
  "rules": [
    {
      "id": "temp-user",
      "name": "用户临时文件",
      "group": "cache",
      "tier": "L1",
      "target": { "kind": "knownFolder", "folder": "LocalAppData", "relative": "Temp" },
      "strategy": { "kind": "purgeContents", "olderThanDays": 7 },
      "requiresAdmin": false,
      "defaultChecked": true,
      "services": [],
      "guard": [{ "kind": "notInstalling" }],
      "consequence": "仅删除 7 天前、且当前未被占用的临时文件。不会删除 Temp 目录本身（它可能是重定向链接）。",
      "undo": "none"
    },
    {
      "id": "recycle-bin",
      "name": "回收站",
      "group": "system",
      "tier": "L1",
      "target": { "kind": "shellRecycleBin" },
      "strategy": { "kind": "shellEmptyRecycleBin" },
      "requiresAdmin": false,
      "defaultChecked": false,
      "services": [],
      "guard": [{ "kind": "confirmUnrecoverable" }],
      "consequence": "永久删除回收站内所有内容，不可撤销。内容本就是你已删除的文件，其中可能有你还想恢复的。",
      "undo": "none"
    }
  ]
}
```

### 5.3 `target.kind` 的四种子类

**禁止通配符跨越用户目录**，禁止相对路径穿越。

| kind | 含义 | 说明 |
|---|---|---|
| `knownFolder` | `SHGetKnownFolderPath` + 相对子路径 | **不用字符串拼 `%LOCALAPPDATA%`**：用户配置重定向、OneDrive 接管时这些目录根本不在 C 盘，拼字符串必然找错地方 |
| `env` | 展开环境变量后取固定子路径 | 仅允许 `TEMP`、`TMP`、`LOCALAPPDATA`、`APPDATA`、`PROGRAMDATA`、`SYSTEMROOT` 白名单变量 |
| `fixedPath` | 字面绝对路径 | 需通过红线校验 |
| `shellRecycleBin` | 虚拟目标，不可有 `relative` | 强制走 Shell API |

### 5.4 红线（运行时派生，规则无权覆盖）

**绝不写 `C:\Windows` 这类字面量。** 系统装在 `D:\Windows` 的机器上，字面量红线全部失效——一条 `target: {kind: env, var: SYSTEMROOT, relative: "System32"}` 的规则（无论有意还是写错）会被放行。红线是全篇最不能硬编码的地方。

```rust
/// 红线在进程启动时一次性派生并 canonicalize。
/// 派生源：环境变量 + KnownFolder，而非字面量。
fn red_lines() -> Result<Vec<PathBuf>, SafetyError> {
    let roots = [
        env::var("SystemRoot"),          // 例：D:\Windows
        env::var("ProgramFiles"),
        env::var("ProgramFiles(x86)"),
        env::var("ProgramData"),
        env::var("windir"),              // 与 SystemRoot 冗余，作为交叉校验
    ];
    let mut out = Vec::new();
    for r in roots.into_iter().flatten() {
        out.push(canonicalize(PathBuf::from(r))?);
    }
    // 卷级路径：$Recycle.Bin / $SysReset / Recovery 挂在 %SystemDrive% 下
    let drive = env::var("SystemDrive")?;               // 例：D:
    for name in [r"$Recycle.Bin", r"$SysReset", "Recovery"] {
        out.push(canonicalize(PathBuf::from(format!(r"{drive}\{name}")))?);
    }
    // 敏感数据目录（KnownFolder，跨用户）
    for f in [FOLDERID_ProgramData] {
        out.push(canonicalize(known_folder(f)?)?.join("Microsoft").join("Crypto"));
    }
    Ok(out)
}

/// 内部关键子路径：这些不单独作为根，而是在命中红线根后按子路径判定
const CRITICAL_SUBPATHS: &[&str] = &[r"WinSxS", r"Installer", r"servicing",
    r"assembly", r"Microsoft.NET", r"catroot2", r"System32\config",
    r"System32\DriverStore", r"Boot", "Fonts"];
// 以及 ProgramData 下的 Package Cache / Microsoft\Windows Defender / Windows\Start Menu

/// 红线之内唯一允许精确命中的路径。必须精确匹配，绝不前缀匹配。
/// 同样派生，不写字面量。
fn exact_allow() -> Result<Vec<PathBuf>, SafetyError> {
    Ok(vec![ known_folder(/* System */)?.join("Temp") ])   // 例：D:\Windows\Temp
}

/// 这些文件名即使出现在允许目录内也必须拒绝（防误伤与系统保护）。
const PROTECTED_FILE_NAMES: &[&str] = &[
    "pagefile.sys", "swapfile.sys", "hiberfil.sys", "DumpStack.log.tmp",
    "bootmgr", "BOOTNXT", "ntldr",
];
```

**红线判定必须两级**：先判"是否落在某个红线根之下"，再判"其子路径是否命中 `CRITICAL_SUBPATHS`"。仅靠第一级，`%SystemRoot%` 会把 `%SystemRoot%\Temp` 也保护掉（而它需要放行）；仅靠第二级，则漏掉整个 `%ProgramFiles%`。

**`exact_allow()` 必须精确匹配而非前缀匹配**——否则 `%SystemRoot%\Temporary`、`%SystemRoot%\TempTrap` 会被一并放行，红线形同虚设。

**派生结果需做交叉校验**：`SystemRoot` 与 `windir` 若不一致则拒绝启动清理功能（可能是环境被污染或被劫持的信号）。

### 5.5 分级模型

四级（含只读），加两个正交维度：

| 级别 | 定义 | 典型目标 | 默认勾选 | 二次确认 | 提权 |
|---|---|---|---|---|---|
| **L0** | 只读扫描 | 全部 | — | 无 | 否 |
| **L1** | 删除后系统无副作用 | 用户 TEMP、缩略图/图标缓存、D3DSCache、CrashDumps、开发缓存、updater 残留、回收站 | 是 | 无（勾选即执行） | 否（回收站见 §9.4） |
| **L2** | 需管理员，有可感知的功能性后果 | `Windows\Temp`、`SoftwareDistribution\Download`、传递优化、WER、内存转储、字体缓存、DISM 组件清理、`Windows.old` | **否** | 逐项展开后果 + 确认框 | 是 |
| **L3** | 不可逆或移除恢复能力 | `DISM /ResetBase`、`vssadmin` 删还原点、关保留存储、`powercfg /h off` | **否** | **输入确认文字** | 是 |

**正交维度 1 · 授权**：用户态 / 需提权
**正交维度 2 · 可撤销**：永久删除 / 可隔离恢复

UI 必须把这两个维度**视觉化区分**——用户看到"删除"默认期待可恢复，这是明确的产品风险点。

> **"默认勾选"有例外**：回收站虽归入 L1（删除后系统无副作用），但**默认不勾选**，因为它装的是用户已删除的文件、可能还有人想恢复的东西，且不命中用户数据 KnownFolder 的保护。详见 §5.6 与 §9.4。

### 5.6 目标性质决定删除策略（I6 / I12 的落地）

**判定必须按下列顺序短路，顺序即优先级**（对应 I12）：

| 优先级 | 目标性质 | 判定条件 | 删除策略 |
|---|---|---|---|
| **1（最高）** | 用户数据目录 | 命中 `FOLDERID_Documents` / `Downloads` / `Desktop` / `Pictures` / `Videos` / `Music` 任一，**或其子路径** | **永久删除的代码路径不存在**；仅隔离 + 二次确认。**无论规则表怎么写** |
| **2** | 未知目录 | 不在规则表中（通用发现命中） | 只能进隔离区 |
| **3（最低）** | 可再生缓存 | 在规则表中，且 `group == "cache"` | 永久删除 |

**优先级 1 必须先判**：否则一条指向 `Documents` 且 `group: "cache"` 的规则会走"永久删除"分支。判定目标是否属于用户数据目录时，要判**整条路径是否落在其下**，不只是相等。

**`group` 是封闭枚举，不是自由字符串**（早期示例里的 `"user-cache"` / `"system"` 属未定义值，校验器无法据此判定）：

```
group ∈ { "cache", "system", "user-adjacent" }
```

- `cache` —— 可再生缓存，允许永久删除
- `system` —— 系统级目标，一律需管理员 + 逐项确认
- `user-adjacent` —— 疑似邻近用户数据，一律只允许隔离

规则校验器对未知 `group` 值**拒绝加载**（fail-closed，与 I2 一致）。

**回收站是特例，需单独声明**：`$Recycle.Bin` 属系统卷路径，不命中用户数据 KnownFolder，因此**绕过优先级 1 的保护**。而它装的是用户已删除的文件，其中可能有用户还想恢复的东西。因此回收站规则：

- 默认**不勾选**（与其他 L1 项相反）
- 执行前单独确认一次，文案明示"内容不可恢复"
- 见 §9.4

## 六、三道安全闸（地基）

### 6.1 闸一：路径规范化与归属校验

```rust
/// 任何进入删除引擎的路径都必须先过这里。
/// 返回规范化后的路径，或说明拒绝原因。
pub fn resolve_and_verify(rule: &CleanRule) -> Result<PathBuf, SafetyError> {
    // 1. 按 rule.target 解析（knownFolder 走 SHGetKnownFolderPath）
    let raw = resolve_target(&rule.target)?;

    // 2. ★ 形态拒绝必须在规范化之前。
    //    \\?\ 会绕过 Win32 规范化：若不先拒绝，`\\?\D:\Windows\Temp\..\System32`
    //    里的 `..` 不会被折叠，后续红线比对拿到的是未规范化的字符串，红线可能失配。
    //    UNC 同理（会删到网络位置）。见 §7.3 的前缀使用约定。
    if raw.has_device_prefix() { return Err(SafetyError::DevicePathRejected); }
    if raw.is_unc()           { return Err(SafetyError::UncRejected); }

    // 3. 展开 .. 与 8.3 短名（D:\PROGRA~1 必须还原成长名再比较）
    let normalized = canonicalize(&raw)?;

    // 4. 拒绝根目录形态
    if normalized.is_root() || is_protected_root(&normalized) {
        return Err(SafetyError::ProtectedRoot);
    }

    // 5. 红线两级校验（按路径分隔符边界，不用字符串 StartsWith）
    if hit_red_line(&normalized) && !hit_exact_allow(&normalized) {
        return Err(SafetyError::RedLine);
    }

    // 6. 保护文件名
    if let Some(name) = normalized.file_name() {
        if PROTECTED_FILE_NAMES.iter().any(|p| name.eq_ignore_ascii_case(p)) {
            return Err(SafetyError::ProtectedFile);
        }
    }

    // 7. ★ 必须是固定卷（非网络盘、非可移动盘）
    if !is_fixed_volume(&normalized)? {
        return Err(SafetyError::NotFixedVolume);
    }

    // 8. ★ 根身份检查：打开句柄取最终真实路径，确认它仍是它自己。
    //    这里只覆盖"根这一层是否被重定向"；遍历过程中每一层由闸二（§6.2）负责。
    //    两者互补、缺一不可 —— 不存在"唯一的 junction 防线"。
    let final_path = get_final_path_by_handle(&normalized)?;
    if !paths_equal_ci(&final_path, &normalized) {
        return Err(SafetyError::RootRedirected { got: final_path });
    }

    Ok(final_path)
}
```

**闸一与闸二的分工（两者互补，不可互替）**：

| | 覆盖范围 | 若不做的后果 |
|---|---|---|
| 闸一第 8 步 | **仅根**这一层是否被重定向到别处 | 根是 junction 时（如 `%TEMP%` 被用户搬到别的盘），删除会发生在目标位置，而白名单校验对象与实际删除对象不一致 |
| 闸二（§6.2） | 遍历过程中**每一层子目录** | 子树内部的 junction 会被跟随，删掉链接指向的真实数据 |

**第 5 步的边界匹配为什么必须单独实现**：

```rust
// 错误做法：字符串前缀比较。
// 它会把 %SystemRoot%\Temporary、%SystemRoot%\TempTrap 之类一并放行 ——
// 一旦红线判定写成这样，红线就形同虚设。
// 正确做法：按路径分隔符边界比较
fn path_starts_with_boundary(path: &Path, root: &Path) -> bool {
    path == root || path.starts_with(root) // Path::starts_with 已按组件比较
}
```

### 6.2 闸二：不跟随重解析点

**决策记录**：早期方案建议"优先用 `IFileOperation`（Shell 语义，与资源管理器同一代码路径）"。复查后**不采用为主路径**，理由：

1. 该依据（Shell 语义天然不跟随重定向）来自调研结论，**未经验证**；
2. 更关键的是，它与我们的三个硬需求冲突——**dry-run 预览、逐文件"成功/跳过/失败"分类、精确进度**。Shell API 给不了这个粒度，而这三点是"让用户自证没删错"的全部依据。

改为自写递归（核心防护只有二十行）：

```rust
fn delete_tree(root: &Path, ctx: &mut Ctx) {
    // 枚举失败（权限/目录已消失）不中断整棵子树，只记一条失败
    let entries = match read_dir_robust(root) {   // FindFirstFileExW + FindExInfoBasic
        Ok(it) => it,
        Err(e) => { ctx.record_failed(root, FailReason::EnumFailed(e)); return; }
    };

    for entry in entries {
        let path = entry.path();
        if ctx.cancelled() { return; }

        // ★ 必须重新查询属性，不能用枚举器缓存的 find_data —— Windows 上不可靠，
        //   这是 Chromium DeletePathRecursively 数据丢失事故的根因。
        //   查询失败（枚举后已被删、无权限）只记一条失败并继续，绝不用 `?` 中断整棵树。
        let attrs = match GetFileAttributesW(&path) {
            Ok(a) => a,
            Err(e) => { ctx.record_failed(&path, FailReason::StatFailed(e)); continue; }
        };
        if attrs & FILE_ATTRIBUTE_REPARSE_POINT != 0 {
            // 是链接本身：删链接，绝不进入。
            ctx.record_reparse_skipped(&path);
            remove_link_only(&path, attrs, ctx);   // 目录 RemoveDirectoryW / 文件 DeleteFileW
            continue;
        }

        if attrs & FILE_ATTRIBUTE_DIRECTORY != 0 {
            delete_tree(&path, ctx);
            // 直接删并容忍 ERROR_DIR_NOT_EMPTY（说明子树里有跳过项，目录留着是对的）。
            // 不用"先判空再删"—— 那是两步操作，中间存在竞态。
            if let Err(e) = RemoveDirectoryW(&path.with_long_path_prefix()) {
                if e.code() != ERROR_DIR_NOT_EMPTY {
                    ctx.record_failed(&path, FailReason::Other(e.code()));
                }
            }
        } else {
            delete_file_tolerant(&path, attrs, ctx);
        }
    }
}
```

**决策记录 · 只读属性文件**：`FILE_ATTRIBUTE_READONLY` 会让 `DeleteFileW` 返回 `ERROR_ACCESS_DENIED`，而 `%TEMP%` 里只读文件相当常见。两种选择的取舍：

| 选择 | 效果 | 风险 |
|---|---|---|
| **默认跳过只读文件**（本方案采纳） | 覆盖率下降，但绝不改变文件的既有属性 | 无 |
| 先清只读位再删 | 覆盖率更高 | 修改了本不属于我们的文件属性；若删除随后失败，文件被留成"可写"状态 |

采纳**默认跳过**，并在报告中单列 `ReadOnlySkipped` 计数与文案提示（"N 个只读文件被跳过，如需清理请手动解除只读"）。这样既保守，又不让用户误以为工具"什么都没干"。

**可选加固**：Windows 11 的 `DeleteFile2` 支持 `FILE_FLAG_DISALLOW_PATH_REDIRECTS`（`0x00010000`），可让路径中任何一段被重定向时直接失败。作为**纵深防御**加上，但不能替代上面的属性检查。

### 6.3 闸三：占用即跳过

```rust
fn delete_file_tolerant(path: &Path, attrs: u32, ctx: &mut Ctx) {
    // 只读文件默认跳过（见上节决策记录），不尝试改属性
    if attrs & FILE_ATTRIBUTE_READONLY != 0 {
        ctx.record_skipped(path, SkipReason::ReadOnly);
        return;
    }

    match DeleteFileW(&path.with_long_path_prefix()) {
        Ok(()) => ctx.record_deleted(path),
        Err(e) => match e.code() {
            ERROR_SHARING_VIOLATION | ERROR_LOCK_VIOLATION => {
                // I5：记入"跳过"，不重试、不强删
                ctx.record_skipped(path, SkipReason::InUse { holder: ctx.probe_holder_sampled(path) });
            }
            ERROR_ACCESS_DENIED => {
                // 注意：可能是权限，也可能是受控文件夹访问(CFA)拦截，见 §9.3
                ctx.record_failed(path, FailReason::AccessDenied);
            }
            _ => ctx.record_failed(path, FailReason::Other(e.code())),
        },
    }
}
```

**明确不做的事**（每条都有真实事故支撑）：

| 不做 | 原因 |
|---|---|
| 重试 | 占用是稳态，重试只是浪费 IO 并延长任务 |
| 强删 / 改 ACL / `takeown` | 改系统目录属主会在后续更新中引发难以诊断的问题 |
| 删一半 | 半毁的目录树比没删更危险 |
| 自动调 `RmShutdown` 关占用进程 | 丢失用户未保存数据；且这是勒索软件（Akira）用过的同款手法 |
| `PendingFileRenameOperations` 延迟删除 | 队列**只增不减**，有多次失败启动后累积、在下次健康重启时误删正常文件的真实案例 |
| 删除目录本身 | 只清内容。删掉 `Temp` 目录会破坏 `%TEMP%` 默认路径，导致安装程序报错 |

### 6.4 占用者探测（必须采样，不能逐文件调用）

`rstrtmgr.dll` 的 Restart Manager 可用于**诊断与提示**：

```
RmStartSession → RmRegisterResources → RmGetList（需调两次，先取个数）→ RmEndSession
```

用途仅限"告诉用户是谁占着"，**绝不调用 `RmShutdown`**。若探测失败或过慢，降级为只报"被占用"。

**成本约束**：一次 session 的建立+注销是重量级操作（涉及跨进程查询）。若对每个删除失败的文件都调一次，在 `%TEMP%` 这种数千文件的场景下会让清理时间膨胀一个数量级。

**采样策略**：

- 每次 job 最多探测 **N 次**（默认 20）
- 同一 rule 内**按占用者名称去重**——一旦探到"chrome.exe 占用"，后续同 rule 内的 InUse 不再重复探测
- 首次探测后若连续 K 次结果相同，则停止探测，只标注"同前"
- **批量**优于逐个：对同一目录下的多个失败文件，一次性 `RmRegisterResources` 注册全部路径，一次 `RmGetList` 取回结果

这样既保留了"告诉用户该关什么程序"的价值，又不让诊断本身成为瓶颈。

### 7.2 长任务与进度上报（对标 `updater`）

**单一事件 + 全量快照**，不做 `xxx-progress` / `xxx-done` / `xxx-error` 三条：

**必须有的三个机制**（照抄 `updater` 已被守卫测试覆盖的实践）：

| 机制 | 作用 | 参考 |
|---|---|---|
| 节流上报 | 按百分比或 MiB 里程碑上报，未跨刻度不上报 | `updater` 的 `push_reportable` |

| 重入闸门（I9） | 判定与置位在同一条 `compare_exchange` 上 | `updater` 的 `try_begin_install` |

### 7.3 长路径处理（入参拒绝、出参加前缀）

`\\?\` 前缀的**两个方向必须分开处理**，早期文档在这点上表述矛盾：

| 方向 | 场合 | 规则 |
|---|---|---|
| **入参** | 来自规则解析的路径进入闸一 | 一旦出现 `\\?\` 或其它设备前缀，**立即拒绝**（在规范化之前，见 §6.1 第 2 步）。因为 `\\?\` 会绕过 Win32 规范化，`..` 不会被折叠，后续红线比对拿到的是未规范化字符串 |
| **出参** | 我们自己拼给 Win32 API 的路径 | 长度 ≥ 260 时**才加** `\\?\`，且**必须在规范化完成之后加**——`\\?\` 不做 `.` / `..` / 正斜杠的规范化 |

其余要点：

- **运行时检测** `HKLM\SYSTEM\CurrentControlSet\Control\FileSystem\LongPathsEnabled`，**不假设 Win11 默认开启**；
- 该设置**按进程缓存**（首次 Win32 文件调用时读取），改了也需新进程生效；
- 注意 `.NET` 与 shell 行为可能仍受 260 限制；
- `\\?\` 前缀**不能**用于 `shellRecycleBin` 这类 Shell API 路径（Shell 不认设备路径）。

### 7.4 服务状态机（I10）

需要停服务的规则（`SoftwareDistribution\Download` → `wuauserv` + `BITS`；传递优化 → `dosvc`；字体缓存 → `FontCache`）：

```
1. 记录每个服务的：启动类型 + 当前运行状态
2. 停止（若本来就已停止，则不停、也不启动回来）
3. 执行清理
4. 还原：恢复原启动类型，恢复原运行状态
5. 任一步失败：仍然执行第 4 步（错误路径不得绕过还原）
```

**护栏**：执行前检测"有更新正在安装 / 有待重启"则**直接拒绝执行该规则**，而不是冒险。检测方式：`wuauserv` 正在运行且有 pending 的 `RebootRequired` 标记。

## 八、通用占用发现（通用性的实现）

### 8.1 为什么必须有

规则库只能覆盖我们知道的东西。实测中，一台机器上**最大的单一垃圾可能完全不在任何现成清理清单里**（本次调研在开发机 `%TEMP%` 下发现一个 17 GB、1935 个文件、每天增长 5.3 GB 的未知目录）。这类问题只能靠发现能力捞出来。

### 8.2 朴素枚举（用户态，P4 交付）

- 从选定卷根 BFS 下钻，**深度限制**（默认 4 层，可调）
- 跳过：红线前缀、重解析点（不进入）、已知的不可读目录
- 统计每个目录的**大小 + 文件数 + 修改时间分布**
- 用 `FindFirstFileExW` + `FindExInfoBasic`（跳过短名解析，显著提速）
- **限制并发、标记低 IO 优先级**，避免打满磁盘队列

### 8.3 MFT 枚举（可选，管理员模式）

`FSCTL_ENUM_USN_DATA` 直接枚举 NTFS MFT，是 WinDirStat 级速度的真正来源。**但它需要管理员权限**（需打开卷句柄），且仅限 NTFS。

> **与提权时序的关系**：提权排在 P6，因此 **P4 只能交付朴素枚举**。不为了性能提前扩大权限面——这是刻意的排序取舍。管理员模式作为 P6 的可选加速项。

### 8.4 增量分析（看门狗的数据来源）

每次扫描存快照（目录 → 大小 / 文件数 / 时间戳），保留最近 N 次。与历史对比得出：

- **绝对占用**：Top N 大目录
- **增长速率**：单位时间增量 Top N ← **这一项才是有用的**，它把"一直很大的目录"和"正在失控的目录"区分开

### 8.5 删除入口与 `discovery_id`（I1 与 I6 的落地）

**问题**：I1 要求"前端绝不传路径"，但本节的删除目标**不在规则表中，没有 `rule_id` 可传**——用户确认的是路径，不是 id。早期文档没有为此建立机制，实现时必然破例传路径，I1 就废了。

**机制**：后端在扫描时为每个发现的目录签发 `discovery_id`，并在**后端内存中持有 `discovery_id → 路径` 的映射**。前端只能回传 `discovery_id`。

```rust
/// 扫描结果常驻于后端状态中；前端只拿到 id 与展示用元数据。
pub struct DiscoveryEntry {
    pub id: DiscoveryId,          // 后端签发，如 "d-7f3a2c"
    pub display_path: String,     // 仅供展示
    pub bytes: u64,
    pub delta_7d: i64,
    pub is_user_data: bool,       // 命中用户数据 KnownFolder（优先级 1）
}

/// 前端删除请求只带 id。后端按 id 找回路径。
#[tauri::command]
fn quarantine_discovery(discovery_id: String, ...) -> Result<(), String> {
    let path = state.resolve_discovery(&discovery_id)?;   // 查不到 = 拒绝，不 fallback
    ...
}
```

- `discovery_id` **只对当前扫描结果有效**，重新扫描即全部作废（防止过期 id 命中错路径）
- 查不到 id 一律**拒绝**，绝不回退成"用 id 当路径"
- 映射表**只存在内存**，不落盘，避免成为"路径注入"的入口

在此前提下，删除必须用户显式确认，且：

1. 该目录成为**单次临时授权根**（只对本次 job 有效，不写入规则表）；
2. **仍然走三道闸**（闸一至闸三原样适用）；
3. **只能进隔离区，不能永久删除**（因为它不在规则表中，属"未知目录"，见 §5.6 优先级 2）；
4. UI 必须明示"此目录不在规则库中，删除后果由你判断"；
5. 命中用户数据 KnownFolder（`is_user_data == true`）时额外二次确认，且**永久删除的代码路径根本不存在**（§5.6 优先级 1）。

**对应的守卫测试**（§15.5）：`src/tools/system-cleaner/` 与 `src/constants/diskCleanupConfig.ts` 中不得出现路径字面量；`quarantine_discovery` 的签名中不得接受路径参数。

## 九、提权与特权操作

### 9.1 契约（I7 / I11）

**先说清两个必须堵的漏洞**——早期文档的契约在这里是有洞的：

| 漏洞 | 攻击方式 | 早期设计的错误 |
|---|---|---|
| **(a) 把非特权方可写的数据当授权依据** | `%APPDATA%` 用户完全可写。攻击者预先放置 `<jobId>.json`，再诱导提权进程读取并据其行动 | 早期设计让提权进程"读 job 文件，校验 nonce"。但 nonce 是主程序写进同一个可写文件的——**输入来源本身不可信**，比内容是否安全更重要 |
| **(b) 提权进程的文件写入可被符号链接重定向** | 攻击者预先在 `<jobId>.result.json` 路径建符号链接指向系统文件，提权进程**以管理员身份覆写它** ⇒ 任意文件写 | 早期设计让提权进程直接写 `%APPDATA%` 下的结果文件。`%APPDATA%` 正是此类攻击的典型目标位置 |

**修正后的契约**：

```
主程序（非提权）
  ├─ rule_id 列表走命令行传递
  │   ShellExecuteW("runas", current_exe,
  │                 "--disk-cleanup-elevated --job <jobId> --rules <id1,id2,...>")
  │   ★ rule_id 是受控标识符（来自签名规则表），不是路径，不违反 I7
  │   ★ 提权进程的"要做什么"完全由命令行决定，不读任何用户可写的文件
  │   返回值 ≤ 32 表示失败（用户拒绝 UAC / 被策略阻止）→ 降级为只做 L1
  └─ 轮询结果文件

提权进程（同 exe，不同启动参数）
  ├─ 校验每个 rule_id 存在于已签名规则表中 —— 不存在则整体拒绝
  ├─ ★ 从规则表解析路径（命令行里根本没有路径）
  ├─ 走同样的三道闸
  ├─ ★ 结果写入防重定向（见下）
  └─ 退出
```

**结果写入的防重定向要求（I11）**：

```rust
/// 提权进程写结果文件必须同时满足：
///   1. 目标目录由提权进程自己创建于 %ProgramData% 下，并设 ACL 为仅 Administrators 可写
///      —— 非特权用户无法在该目录内预置符号链接
///   2. 若目标目录已存在，校验其不是重解析点（否则攻击者可能提前造好链接目录）
///   3. 文件用 CREATE_NEW 打开，已存在则失败 —— 绝不覆写
///   4. 打开时带 FILE_FLAG_OPEN_REPARSE_POINT，确保不跟随末段链接
fn open_result_file_secure(dir: &Path, name: &str) -> Result<File, ElevateError>
```

**关于 nonce**：修正后 nonce 只用于**关联结果文件与本次请求**（防止读到上一次的陈旧结果），**不再承担任何授权作用**。授权完全由"rule_id 必须在签名规则表中"这一条提供。

**为什么不用 IPC / 命名管道**：那是新的攻击面。命令行 + 单向结果文件最简、最可审计，且天然满足"提权进程不把不可信输入当授权"。

**为什么不用"提权进程内二次确认 UI"**：这是一个可选加固，但它把"是否执行"的决定权交给了用户，而不能替代上述结构性问题。若采纳，应作为第 4 层防线，不是唯一防线。

### 9.2 结果回传

结果文件包含每个 rule 的 `scanned / deleted / skipped / failed / freedBytes` 与**原因分类**。主程序读取后合并进审计日志并 publish 给前端。

### 9.3 受控文件夹访问（CFA）检测

开启 CFA 时，对 `Documents` / `Pictures` / `Desktop` 等的删除或移动会返回**拒绝访问，但这不是权限问题，是 Defender 拦截**。把它当权限错误处理会导致"反复重试 / 建议提权 / 提权后依然失败"的错误循环。

**检测途径（明确指定，不用"等价 API 或注册表"这种含糊说法）**：

| 优先级 | 途径 | 说明 |
|---|---|---|
| 主 | WMI 类 `MSFT_MpPreference` 的 `EnableControlledFolderAccess`，命名空间 `root\Microsoft\Windows\Defender` | 与 `Get-MpPreference` 同一数据源；标准用户即可读取 |
| 交叉校验 | 注册表 `HKLM\SOFTWARE\Microsoft\Windows Defender\Windows Defender Exploit Guard\Controlled Folder Access` → `EnableControlledFolderAccess` | 该键可能受 ACL 限制，读不到不算失败 |
| 事后确认 | 事件日志 `Microsoft-Windows-Windows Defender/Operational` 事件 ID 1123 | 仅在需要精确确认"哪次拒绝是 CFA 造成"时使用 |

```rust
/// 取值语义：0 = 关闭，1 = 开启，2 = 仅审核（不拦截）。
fn detect_cfa() -> CfaState { /* WMI 主 + 注册表交叉校验 */ }
```

**判定规则**：

- `CfaState::On` 且目标是用户数据 KnownFolder 或 `ProgramData` 下的受保护路径 → **在尝试之前**就拒绝并给出正确提示，不要等失败后再猜
- 已开启 CFA 时，`ERROR_ACCESS_DENIED` 且目标位于用户数据目录 → 归类为 `FailReason::CfaBlocked`，**不是** `AccessDenied`
- 检测失败（读不到）→ 归类为 `AccessDenied` 但**提示文案同时列出两种可能**，不做过度断言

UI 文案必须区分：「这是 Windows Defender 的受控文件夹访问拦截，**提权也无法解决**；要清理此类目录需在 Defender 的"受控文件夹访问"设置中调整」。

### 9.4 回收站

回收站里本来就是用户已删的文件，**是全清单里最安全、最易解释、收益又最大的目标之一**，因此不排在最后。

- 必走 `SHQueryRecycleBin`（先查条目数）+ `SHEmptyRecycleBin`（`SHERB_NOCONFIRMATION | SHERB_NOPROGRESSUI | SHERB_NOSOUND`）
- **不能**按文件系统路径删 `%SystemDrive%\$Recycle.Bin\<SID>`（破坏 shell 一致性）；该路径同时是红线（§5.4）
- **默认不勾选**（与其他 L1 项相反）。理由见 §5.6：回收站内容不命中用户数据 KnownFolder，因此**绕过了优先级 1 的保护**，而里面可能有用户还想恢复的东西。执行前单独确认一次，文案明示"不可恢复"
- ⚠️ **待验证**：`SHEmptyRecycleBin` 是否必需提权存在不确定性（调研结论与"标准用户可清空自己回收站"的直觉有出入）
  - **实现策略**：用户态先尝试，失败再降级到提权路径，**不阻塞开发**
  - **不做的验证**：不在用户真实回收站上做实验；如需验证须先获得用户明确同意
- **分级归属的例外记录**：本条在 §5.5 的分级表里划为 L1（系统无副作用），但因上述"默认不勾选 + 单独确认"的额外约束，它在 UI 上的行为**不等同于其他 L1 项**

## 十、隔离区

### 10.1 设计

```
%APPDATA%\com.levitaire.app\quarantine\<jobId>\
  ├─ manifest.json      # [{ originalPath, size, movedAt, ruleId|discoveryId, isUserData }]
  └─ <按序号存放的文件/目录>
```

- **同卷 move**（元数据操作，秒级、原子）。同卷判定**必须拿目标实际所在卷与隔离区所在卷比较**，不能假设目标是 C 盘
- 跨卷才降级为 copy + 校验 + 删源（并明示慢）；**校验失败必须保留源文件**，绝不出现"源已删、副本不完整"
- 保留期默认 **7 天**，可在设置中调整为 0（立即彻底删）/ 14 / 30
- **恢复**：按 manifest 移回原路径（原路径已被占用时提示，不覆盖）
- **彻底删除**：用户主动、或到期自动
- manifest 中的 `isUserData` 落地 §5.6 优先级 1 的"仅隔离"约束——恢复界面对这类条目应更醒目

### 10.2 空间账目必须诚实（关键）

**隔离区的"释放空间"是延迟的。** 同卷 move 不释放任何空间，要等保留期到期真正删除后才释放。而早期文档把它算进了"可安全释放 55 GB"，这是**承诺一个兑现不了的数字**。

UI 必须把总账拆成两栏：

```
可立即释放          42.7 GB    ← 规则类缓存，永久删除
隔离区暂存         12.3 GB    ← 7 天后释放；也可选立即彻底删
  （其中用户数据     2.1 GB    ← 不可立即删，只能等保留期）
```

- 默认保留期 7 天时，**不要把隔离区的量算进"立即释放"**
- 用户选择保留期 0 时，隔离区条目直接走永久删除，此时才计入"立即释放"——但**用户数据条目例外**，即使保留期为 0 也必须先隔离并要求显式确认
- 隔离区自身占用单独显示，避免"清了 10 GB 但隔离区吃了 10 GB"的困惑

> 隔离区比回收站更可控：回收站会占用**等量空间**（与"释放空间"目标自相矛盾），且受回收站配额策略影响，还可能因配额超限被系统策略直接永久删除。

## 十一、看门狗

### 11.1 设计要点

**不盯固定路径，只比对历次快照的增量。** 这样"某目录持续失控"这个模式能被同一套机制捞出来，不需要为每种病写一条硬编码规则。

- 触发条件（两者同时满足）：`单目录大小 > 阈值(默认 2 GB)` **且** `近 7 日增长 > 阈值(默认 1 GB)`
- 频率：默认每天一次，可关闭；**必须低频**，避免自身成为负担
- 运行在低优先级 IO（`PROCESS_MODE_BACKGROUND_BEGIN` 或等价手段）
- 触发后：`tauri-plugin-notification` 发通知 + 面板内高亮，提供「查看」与「隔离清理」两个动作
- 用户可添加自定义监视目录（这是发现能力的补充）

### 11.2 快照存储

`%APPDATA%\com.levitaire.app\cleanup-snapshots\` 下按时间戳存放，保留最近 N 份（默认 30）。需做体积上限，避免自己变成垃圾。

## 十二、审计日志（I8，P2 就交付）

### 12.1 为什么是安全机制而非附加功能

"能精确说出我删了什么、跳过了什么、为什么跳过"是这类工具**唯一的自证手段**，也是出事后的取证依据。它必须从第一个可交付版本就存在。

### 12.2 记录内容

每次 job 一份 JSONL：

```
{ ts, jobId, ruleId|discoveryId, phase,
  action: "deleted"|"skipped"|"readonly-skipped"|"failed"|"reparse-skipped",
  path, size, reason? }
```

外加每个 rule 的汇总与整次 job 的报告。保留策略：默认 90 天或最近 100 次。

**UI 提供**：查看明细、按 rule 筛选、导出、以及"本次清理前可用空间 / 清理后可用空间"的对照。

### 12.3 隐私边界（必须写明）

审计日志记录的是**用户文件系统路径全文**，属隐私数据。约束：

- **纯本地存储**，位于 `%APPDATA%\com.levitaire.app\cleanup-audit\`
- **绝不上传**——不上报、不遥测、不随崩溃报告或更新检查携带。这条与项目既有的用户数据保护约束一致
- **"导出"是用户显式动作**，导出前提示内容包含本机路径
- 提供**一键清空审计日志**，且该动作在设置页可见
- 到期自动删除（90 天 / 100 次），避免长期累积成为隐私面
- 若未来加入"规则热更新上报使用情况"之类的功能，**不得**夹带审计日志内容

**结构约定（与旧版九分区滚动流的差异）**：

1. **三格统计头**合并了旧「磁盘总览 + 空间账目 + 本次明细」三个分区；§10.2 分栏语义不变 ——
   隔离区单独一格，细分账目（本次将新增到隔离区 / 其中属于用户数据）收进**隔离区折叠区**；
   隔离区读失败时该格显示「读取失败」（带 title），不显示 0。
2. **管理员项（requiresAdmin）不进主视图**：勾了也执行不了，展示了只是噪音；
   L2/L3 徽章内联在规则行上（L1 不显示徽章）。
3. **高级分区手风琴**：空间分析（占用发现 + 失控告警 + 不建议清理）/ 隔离区 / 审计日志，
   一次只摊开一个（`openPanel`）；审计的拉取时机挂在折叠行展开上，
   且折叠行**仍在规则表加载失败分支之外**（I8 不变）。
4. **「本次执行」摘要行只在 `phase === "done"` 时出现**（§12.2 前后对照 + 非零关键计数）；
   完整技术计数（只读/链接/未到保留期）在审计日志里。
5. 窗口高度 460：按自然内容高取值；规则更多时中段滚动兜底
   （`.cleaner-scroll` 的 `overflow-y:auto` 仍是**承重**约定，layout 守卫在）。

**核心交互原则**：

1. **预先 dry-run**：点清理前必须已完成扫描，展示"文件数 + 预计释放 + 抽样路径"
2. **数字必须标注为估算**：扫描与执行之间文件系统必然变化，dry-run 数字会过期。UI 不得把它呈现为承诺（对应 §17 验收标准第 12 条）
3. **后果文案强制展示**：`consequence` 字段不允许为空，UI 校验
4. **不可撤销性视觉区分**：永久删除与可隔离恢复在 UI 上必须一眼可分
5. **空间账目分栏**：立即释放 / 隔离区暂存分开显示（§10.2），不得合并成"释放了 X GB"
6. **回收站默认不勾选**，执行前单独确认（§9.4）
7. **不提供"全选 L2"**：避免一键深清
8. **L3 需输入确认文字**
9. **报告页**：成功 / 跳过（含占用者）/ 只读跳过 / 失败（含原因，区分 CFA 与权限），以及"不建议清理"的解释
10. **发现项删除**：只提交 `discovery_id`，UI 明示"此目录不在规则库中，删除后果由你判断"（§8.5）

## 十五、测试计划

### 15.1 蜜罐测试（最高优先级，必须进 CI）

**这是唯一能证明"不跟随重定向"的方法。**

```
1. 建临时目录 A，放哨兵文件 sentinel.txt
2. 在临时目录 B 下建 junction / symlink 指向 A
3. 对 B 执行 delete_tree
4. 断言：sentinel.txt 仍然存在（内容未变）
5. 断言：B 下的链接本身已被删除
6. 断言：审计日志中出现 reparse-skipped 记录
```

覆盖变体：junction、symlink、目录链接、指向网络路径的链接、链接嵌套链接、`%TEMP%` 本身是 junction 的情形。

### 15.2 闸一单元测试

**用例必须以 `%SystemRoot%` 参数化，不能写死 `C:\`** —— 否则测试本身就在强化那个已修的硬编码缺陷。测试应在两套环境变量下各跑一遍：系统盘为 `C:` 与为 `D:`。

| 用例 | 期望 |
|---|---|
| `<Root>\Temp\..\System32` | 规范化后 `..` 折叠，命中红线，拒绝 |
| `<Root>\PROGRA~1`（8.3 短名） | 规范化为长名后命中红线，拒绝 |
| `\\server\share\x` | UNC 拒绝 |
| `\\?\<Root>\Temp` | **设备前缀在规范化之前**即拒绝（验证步骤顺序，不是"规范化后拒绝"） |
| `\\?\<Root>\Temp\..\System32` | 同上，拒绝（此例专门验证"未折叠 `..` 导致红线失配"这一风险） |
| `<Drive>\`、`<Root>`、`<Users>` | 根形态拒绝 |
| `<Root>\Temporary` | **须拒绝**（验证边界匹配，与 `exact_allow()` 的精确例外区分） |
| `<Root>\TempTrap` | 精确例外**不得**前缀匹配，拒绝 |
| `<Root>\Temp` | 精确例外放行 |
| `<Root>\WinSxS`、`<Root>\Installer`、`<Root>\System32\config` | `CRITICAL_SUBPATHS` 命中，拒绝 |
| `<ProgramFiles>\任意` | 红线根命中，拒绝 |
| **`D:\Windows\System32`（系统盘为 D: 的场景）** | **须拒绝** —— 这条专门验证红线已动态派生，未回退成字面量 |
| `SystemRoot` 与 `windir` 不一致 | 拒绝启动清理功能（环境可能被劫持） |
| 页面文件 / 休眠文件 | 保护名单拒绝 |
| 网络盘 / U 盘上的目标 | 固定卷校验拒绝 |
| 根目标是 junction（指向别处） | `RootRedirected` 拒绝 |
| 规则表写入 `<Root>\Installer` | 规则校验器拒绝加载 |

### 15.3 规则校验器测试

校验器一律 **fail-closed**：任何无法判定的情况都拒绝加载（与 I2 一致）。

| 用例 | 期望 |
|---|---|
| 空 `consequence` | 拒绝加载 |
| 缺 `id` / `id` 重复 | 拒绝加载 |
| `requiresAdmin: true` 但 `tier: "L1"` | 拒绝加载（级别与授权不一致） |
| `group` 不在 `{cache, system, user-adjacent}` | 拒绝加载（封闭枚举，§5.6） |
| `group: "cache"` 但 `undo != "none"` | 拒绝加载（缓存类不应可恢复，语义矛盾） |
| 目标命中红线 | 拒绝加载 |
| 目标命中用户数据 KnownFolder，且未显式声明 `group: "user-adjacent"` | 拒绝加载——本工具没有任何正当理由把用户数据目录作为**缓存清理**目标 |
| `tier: "L3"` 且 `defaultChecked: true` | 拒绝加载 |
| `schemaVersion` 高于本程序支持 | 拒绝加载（不猜测未知字段语义） |
| 签名校验失败 | 拒绝加载，并**保留上一份可用规则**（不降级到空表，否则所有清理项消失） |

### 15.4 集成测试

- 占用文件 → 跳过并记录 `InUse`，任务继续
- 只读文件 → 记录 `ReadOnlySkipped`，文件属性未被修改
- 枚举中途文件消失 → 只记一条 `StatFailed`，**子树其余部分继续处理**（验证 §6.2 的容错，verifies 没有回归到 `?` 中断）
- 目录删不干净时 → 容忍 `ERROR_DIR_NOT_EMPTY`，目录保留且不报失败
- CFA 开启 → **在尝试之前**就拒绝并给出正确提示；若绕过预检，`AccessDenied` 须归类为 `CfaBlocked`
- 服务状态还原：清理前后对比 `wuauserv` 的启动类型与运行状态
- 重入闸门：并发发起两次清理 → 第二次被拒绝，不产生中间状态
- 取消：扫描中取消 → 任务干净退出，无部分删除
- **`discovery_id`**：重新扫描后旧 id 失效并被拒绝；伪造/未知 id → 拒绝且**不回退成按路径处理**
- 提权：命令行不含路径；提权进程对未在签名规则表中的 rule_id → 整体拒绝
- **提权结果写入**：预置同名结果文件 → `CREATE_NEW` 失败并拒绝；预置符号链接 → `FILE_FLAG_OPEN_REPARSE_POINT` 使其失败，断言目标文件未被写入（对应 I11）

### 15.5 源码守卫测试（延续项目风格）

新增守卫，防止后续改动破坏不变量：

| 守卫 | 断言对象 | 断言 |
|---|---|---|
| 提权入口不接受路径参数 | `main.rs` 中 `--disk-cleanup-elevated` 启动参数**分支**（注意：它不是 `#[tauri::command]`，而是启动分支，断言对象是分支内解析出的参数集合） | 该分支只解析 `--job`、`--rules` 两类参数；出现 `PathBuf` / 路径形态参数即失败 |
| 提权结果写入必须防重定向 | `disk_cleanup/elevate.rs` | 写结果文件处必须调用 `open_result_file_secure`（文本守卫：禁止裸 `File::create` / `OpenOptions::new().write(true)` 出现在该文件） |

| 不使用 RmShutdown | 全库 | 搜索 `RmShutdown` / `RmRestart` 即失败 |
| 无裸 `Command::new` | 全库 | 复用既有守卫 |
| L3 规则不可默认勾选 | 规则表 JSON | `tier: "L3"` 的项不得带 `defaultChecked: true` |
| 用户数据目录无永久删除路径 | `disk_cleanup/delete.rs` | 断言 §5.6 优先级 1 的判定先于规则表判定（函数调用顺序守卫） |

## 十六、分阶段实施

阶段顺序的关键原则：**安全地基先于功能；权限面扩大尽量后置；每个阶段都能独立验证。**

| 阶段 | 内容 | 交付价值 | 依赖 |
|---|---|---|---|
| **P1 地基** | `safety.rs`（三道闸，含**运行时派生的红线**）+ `delete.rs`（删除引擎，含容错与只读跳过）+ **蜜罐测试** + 闸一参数化单元测试 + 红线不写字面量的守卫 | 无 UI，但**唯一能独立证明正确的模块**；后续所有功能的地基 | 无 |
| **P2 规则与执行** | `rules.rs`（含封闭枚举校验器）+ `audit.rs`（含隐私边界）+ L1 用户级规则 + dry-run 扫描 + 重入闸门 + `consequence` 强制校验 + 面板 UI | **用户态、零风险、可交付**：TEMP、缩略图、开发缓存、updater 残留 | P1 |
| **P3 回收站与隔离区** | `SHEmptyRecycleBin` 命令 + `quarantine.rs` + 隔离区管理 UI + **空间账目分栏（立即释放 / 隔离区暂存）** | 回收站（收益最大的单项之一）+ 未知目录的可恢复删除 | P2 |
| **P4 发现** | `discover.rs` 朴素枚举 + 快照 + Top N / 增量视图 + **`discovery_id` 签发与解析**（§8.5，I1 的关键） | 能发现规则库没覆盖的垃圾——**通用性的兑现** | P3 |
| **P5 看门狗** | `watchdog.rs` + 通知 + 自定义监视目录 | 持续泄漏类问题自动浮出 | P4 |
| **P6 提权与 L2** | `elevate.rs`（命令行传 rule_id + **结果写入防重定向，I11**）+ CFA 检测 + L2 系统项（含 DISM 组件清理，可选 MFT 加速） | 覆盖系统级大头 | P5 |
| **P7 L3 专家项** | `/ResetBase`、还原点、休眠文件、保留存储 | 覆盖最后的长尾 | P6 |

**P6 之前的所有阶段都不提权**，这是刻意的：把"我们能删多少"与"我们有权删多少"解耦，先用零权限的部分把三道闸的正确性在生产环境验证充分。

> **实施进度**：P1 ~ P5 已交付，另有第 7 版的真机修复（回收站量尺寸改造）、
> 第 8 版的缺口闭合（审计界面等），以及第 9 版的全量复查修复。
> 各自的偏差与实测修正见附录 C 的第 3~7 版。
> 其中 `discovery_id`（§8.5）在 P3 就落地了「手动挑目录」这条通路 ——
> 隔离区需要一个生产者，否则这个能力要等到 P4 才被验证。

## 十七、验收标准

### 总体

1. 蜜罐测试全部通过，且**在 CI 中运行**
2. 闸一单元测试全部通过，且**以 `%SystemRoot%` 参数化跑两遍**（系统盘为 `C:` 与 `D:`）

### 安全

6. 规则文件被篡改（注入指向红线的规则）时拒绝加载，且保留上一份可用规则
7. 提权进程收到未授权 rule_id 时**整体拒绝**（不是跳过该项）
8. 任意 junction 场景下哨兵文件零损失
9. `discovery_id` 失效或伪造时拒绝，且**不回退成按路径处理**
10. 清理过程中取消，不留部分删除的目录树
11. 服务状态在清理前后完全一致（启动类型 + 运行状态）
12. 提权写结果文件时，预置符号链接无法造成目标文件被覆写

### 产品

13. 输出包含"不建议清理"分区及其原因说明
14. 不出现"承诺释放 X GB 但实际只释放 Y MB"的情况：
    - 收益估算不用目录遍历累加（`WinSxS` 类一律以官方报告为准）
    - **隔离区暂存量不计入"立即释放"**（§10.2）
15. 审计日志纯本地、可一键清空，且无任何外发路径（§12.3）

## 十八、风险与开放问题

### 18.1 已识别的风险

| 风险 | 说明 | 处置 |
|---|---|---|
| **被安全软件误判** | 删除文件 + 枚举磁盘 + 提权的行为组合与恶意软件相似；`cleanmgr /autoclean` 已被列入 LOLBin 滥用清单，`vssadmin delete shadows` 是勒索软件 T1490 的标准动作 | 安装包签名；L3 项默认不暴露；文档明示可能被拦；不使用 `cleanmgr /autoclean` 作为执行路径 |
| **提权接口的本地攻击面** | 提权进程若读不可信文件、或往可预测路径写文件，会分别构成"提权原语"与"任意文件写" | 已识别并处置：命令行走 rule_id、结果写入防重定向（§9.1、I11）；配集成测试 |
| **收益预期落差** | 很多机器上最大的占用本就不可清理 | §13.2 的"不建议清理"分区是核心交付，不是附属 |
| **规则热更新的信任模型** | 规则可更新 = 可被滥用 | 签名校验 + 红线运行时派生（I3）+ 封闭枚举校验器 |
| **只读文件跳过的用户预期** | 默认跳过只读文件（§6.2 决策记录）会降低清理量，用户可能觉得"工具没清干净" | 报告单列 `ReadOnlySkipped` 计数与文案提示；不静默 |
| **工程规模** | P1~P7 完整实现保守估计上万行含测试，且测试成本高于代码成本 | 分阶段交付，P1 独立可用；每阶段可停 |
| **测试环境要求** | 部分场景（CFA、配置重定向、非 C 盘、UAC 拒绝）需要特定环境 | 手工验收矩阵单列，不阻塞自动化部分 |

### 18.2 开放问题（需进一步明确）

1. **`SHEmptyRecycleBin` 是否必需提权** —— ⚠️ 未确定。实现上按"先用户态、失败降级"处理，不阻塞。**不在用户真实回收站上做实验。**
2. **`IFileOperation` 是否真的不跟随重解析点** —— ⚠️ 未验证。因此不采用为主路径（§6.2），仅在有明确结论后作为可选后端。
3. **规则签名的密钥体系** —— 复用 `updater` 的 minisign 密钥，还是独立一套？独立更安全（更新包与规则包的爆炸半径不同），但多一套密钥管理。
4. **是否要做"修复建议"能力** —— 本次调研中最有价值的产出之一其实是**诊断**（发现某目录每天增长 5.3 GB，并指出这是已知软件缺陷）。这类问题的正确处置是**改配置根治**，而不是每天清理。是否要把"发现 → 诊断 → 建议修复"作为独立能力纳入（例如"该目录疑似 X 软件的已知泄漏，建议 Y"的知识条目），需要单独决策——它属于另一个产品维度。
5. **清理范围是"系统盘"还是"任意盘"** —— 红线已改为运行时派生（I3），因此**系统盘非 `C:` 的场景已不再是安全问题**。但产品范围仍未定：是只清系统盘，还是允许用户选任意盘（多盘下跨卷隔离区会退化为 copy + delete）。
6. **规则覆盖范围的首批清单** —— 首批规则应覆盖哪些软件生态（开发工具链 / 游戏 / 下载工具 / 虚拟机），建议在 P2 开始时按"实测收益 × 安全度"排序确定。
7. **CFA 预检的可用性** —— WMI `MSFT_MpPreference` 在部分企业策略或第三方安全软件接管 Defender 时可能读不到。预检失败时的降级文案（同时列出"权限不足"与"CFA 拦截"两种可能）会不会让用户困惑，需要看实际反馈。
8. **隔离区位置与用户配置重定向** —— 隔离区固定放在 `%APPDATA%` 下。若用户的 AppData 被重定向到别的盘，而清理目标在 C:，同卷假设失效、隔离变成跨卷 copy。是否允许用户指定隔离区位置，需要在 P3 决定。

## 附录 B：术语

| 术语 | 含义 |
|---|---|
| 重解析点 (reparse point) | NTFS 的链接机制，含 junction / symlink / mount point。递归删除时若跟随会删到目标真实数据 |
| 硬链接 (hard link) | 多个目录项指向同一数据块。Explorer 会把每个链接当独立文件计数，导致 `WinSxS` 显示虚高 |
| CFA | Controlled Folder Access，Defender 的受控文件夹访问。拦截表现为"拒绝访问"但非权限问题 |
| LOLBin | Living-off-the-Land Binary，系统自带但可被滥用的可执行文件 |

**A. ★ `BusyGuard::acquire` 把别人正在持有的闸门放开了（第 9 版引入）**

```rust
// 错的
state.try_begin().then_some(Self { state, armed: true })
```

`bool::then_some` 是**按值传参**的：条件为 false 时那个守卫**已经被构造出来又被丢弃**，
`Drop` 照常执行 → `finish()` → `busy = false`。也就是说**每一次被拒绝的抢闸，
都会强行释放当前正在跑的那个任务的闸门**。

后果不是"这次抢闸失败"，而是 **I9 在竞争路径上整体失效**，而且触发条件毫不极端：
用户双击「开始清理」、看门狗轮询、点一下隔离区的恢复 —— 任何一次在任务运行期间的
抢闸尝试都会打开闸门，让第二个删除任务与第一个并发跑起来。连带后果：
`request_cancel` 以 `busy` 为准，取消按钮会静默失效。

已用独立 `rustc` 程序实测复现，改成 `if/else`（`then(|| ...)` 才是惰性的），
并补回归用例 `a_rejected_acquire_never_releases_someone_elses_gate`。

**同一根因的另外两处**（都属"这次改动之外、但同一类缺陷"）：

- `sound/mod.rs` 的 `tick_guard`：`is_tick.then_some(TickInFlightGuard)` —— 非刻度音
  （确认音、提示音）会构造并立刻析构守卫，**把正在飞的那个刻度音的标志清掉**。
  原有用例只断言 `is_none()`，而 `then_some` 的返回值同样是 `None`，抓不到。
  已修 + 用例改成真的去看标志。
- 排查确认没有第三处。

**B. 一个残留空任务目录能让**整个隔离区**不可用（第 9 版引入 + 既有语义分叉）**

`JobQuarantine::begin` 明确把"目录里没有清单"当**第一次使用**，而 `list()` 走的
`read_manifest` 把它当**硬错误** —— 同一件事两种口径。而第 9 版新加的
`drop_empty_job_dir` 是**先删清单再删目录**：`remove_dir` 一旦失败（杀软/索引器持有
句柄、目录里残留 `manifest.json.tmp`）就正好制造出这种目录。

后果：`list()` / `summary()` 全部失败 → 隔离区里所有条目**既看不到也恢复不了**，
`purge_expired` 也**永久静默停止**（读不到清单就什么都不删）→ 隔离区只增不减，
用户只能按提示去手工删目录。

修法：
- `read_manifest` 把「清单文件**不存在**」当空清单（那本来就是正确语义），
  「清单存在却读不出来/解析不了」**仍然报错** —— 后者意味着内容还在而认不出，
  说"隔离区是空的"等于告诉用户东西没了。
- `begin` 直接复用同一份判断，两处口径合并。
- `drop_empty_job_dir` 连 `manifest.json.tmp` 一起收；`purge_all` 顺手扫掉空壳。
- 补 3 条用例：空壳目录不破坏整个隔离区、损坏清单必须报错、清空时**绝不**碰
  没有登记但**有内容**的目录。

**C. 隔离区还有三处"失败后状态不可自愈"**

### 第 9 版（全量代码复查后的修复）

用户要求「再仔细检查所有实施和修改的代码有没有什么问题」，于是对 P1~P5 与第 7、8 版的

**A. 闸一（安全闸）的两个真实放行缺陷**

| 缺陷 | 后果 |
|---|---|
| 设备前缀只认反斜杠写法 | `//?/C:/Windows/System32` 通过第 2 步 → `GetFullPathNameW` 把它规范化成 `\\?\C:\...` → **此后所有前缀比较全线失配**，红线一条都命中不了。已逐条实测复现 |
| 卷级红线只钉在 `%SystemDrive%` 上 | 双系统、或把 Windows 装在 D 盘的机器上，`D:\Windows`、`D:\$Recycle.Bin`、`D:\System Volume Information` **一条都拦不住** |

两条都已修：前者在规范化后**再查一次**设备前缀（并让 `path_key` 主动剥离），
后者把 `Windows` / `Windows.old` / `$Recycle.Bin` / `$SysReset` / `$WinREAgent` /
`Recovery` / `System Volume Information` / `Program Files` / `Program Files (x86)` /
`ProgramData` 扩展到**每一块固定卷**。

红线判定新增回归用例，用自造的"卷根"来测 —— 这条规则没法在真实机器上确定性验证
（谁也不会真去 `D:\Windows` 建东西），所以给卷清单加了 `with_red_volumes_for_tests` 开关。

**B. I9 长任务闸门会被永久锁死**

`try_begin()` / `finish()` 是手写配对，而 `quarantine_discovery` 里跨着一个
`spawn_blocking(...).await?` —— 闭包 **panic** 时返回 `JoinError`，`?` 直接返回函数，
`finish()` 根本执行不到。后果不是"这次失败"，而是**此后每一次扫描、清理、发现都报
"已有一个任务在进行中"，只有重启应用才能恢复**。

修法：引入 RAII 的 `BusyGuard`，把 `start` / `run_job` / `run_discovery` /
`quarantine_discovery` / `watchdog::run_once` / 隔离区三个管理命令全部包上。
`run_job` 与 `run_discovery` 用 `adopt()` 接管 `start()` 交过来的闸门 ——
**真正干活的函数才是闸门的主人**，它 panic 时也要能放开。

顺带：隔离区的 `restore` / `purge` / `purge_all` 原先**不受 I9 约束**，
与正在跑的清理任务并发时，"正往里搬"和"正往外删"会撞在一起。

**C. 用户数据判定 fail-open**

`is_user_data_path` 写的是 `known_folder(...).map(...).unwrap_or(false)`：
`SHGetKnownFolderPath` 一旦失败，结论就变成"这不是用户数据"，而下游正是拿这个布尔值
决定能不能永久删除 —— **一次读取失败会静默地把用户数据降级成普通缓存**。
改为失败即保守判为"是用户数据"（只隔离 + 多一次确认）。

同源的一处：`ensure_com_initialized` 不论成败都缓存 `ready = true`，
一次偶发失败会被记成"已就绪"且**永不重试**。改为只缓存成功
（`RPC_E_CHANGED_MODE` 视为成功）。

| `set_system_cleaner_enabled` | 误报：它由 `registry.ts` 的 `BACKEND_TOOLS` 经 `backendSetterFor(id)` 间接调用，我把 registry.ts 加进扫描面即可 | 修守卫的扫描面 |

### 第 7 版（回收站量尺寸改造）

这一版不是新阶段，是针对第 6 版之后**真机跑起来暴露的问题**做的修复。

**问题：Shell 查询的耗时与数据量无关**

第 4 版给 `SHQueryRecycleBinW` 定了"每卷 30 秒预算 + 超时记未统计"。真机上一跑，两个卷
**全部超时**，而回收站恰好是这台机器上最大的一块。逐层查下去：

| 卷 | 回收站内容 | 本地递归枚举 | `SHQueryRecycleBin` |
|---|---|---|---|
| `C:\` | 66012 个文件 / 13.89 GB | **2.7 秒** | 8.7 秒 |
| `D:\` | 61128 个文件 / 38.61 GB | **0.4 秒** | **240 秒仍未返回** |

同一块 NVMe、都是 NTFS、都健康。文件系统 0.4 秒能数完的东西 Shell 要 4 分钟以上 ——
**差距不在数据量，在 Shell 自己的逐项解析**（很可能在为每个条目解析原始位置，
遇到已不存在的路径就慢慢等）。这种延迟不可预测（8.7 / 30 / 240 秒都出现过）、
不可取消，**提高预算治不了它**。

更要命的是超时后的返回值：`query_volumes` 在超时时把该卷记进 `skipped_volumes`、数字按 0 算，
而真机上 30 秒超时**返回的就是 0 项 / 0.0 B** —— 与"回收站是空的"在界面上分不出来。

**改动：量尺寸与清空分开，各用各的手段**

| 做什么 | 手段 | 结果 |
|---|---|---|
| **量尺寸** | 只读枚举 `<盘>:\$Recycle.Bin\*` | 实测 **17.5 秒**（两卷 12.7 万文件）= 有界、可取消、可报进度 |
| **清空** | `SHEmptyRecycleBinW` | 不变。绝不按文件系统路径删 |
| **复核释放量** | 清空后再枚举一次 | 比再查一次 Shell 更快也更可靠 |
| **兜底** | Shell 查询 | 只在"一个 `$Recycle.Bin` 都读不到"时才用 |

改动后实测：`C:\` 13,890,360,811 字节 / 66012 文件，`D:\` 38,609,658,264 字节 / 61128 文件，
与 `robocopy /L /XJ` 的数**完全一致**；同一时刻 Shell 查 C: 仍然 30 秒超时。

**三条已知的口径差异（必须如实告诉用户）**

| # | 差异 | 处置 |
|---|---|---|
| 1 | **其它账户的回收站读不到**（`S-1-5-18` 等 ACL 拒绝）→ 少报。本机 C 盘 2 个、D 盘 1 个 | 在报告里明说"未计入"，并点明"那部分非管理员也清不掉，所以上面的数字就是本次能释放的量" |
| 2 | **计数口径不同**：资源管理器按"回收条目"计（删一个含 1000 文件的目录算 1 项），我们按**文件**计 | 字节数能对上（C 盘实测 13.890 vs Shell 的 13.881 GB）。界面按文件计 |
| 3 | **硬链接会略微多报**（回收站里的文件若还有别的链接，删掉这份并不真正释放空间）| 记为已知限制 |

**顺带修掉的两个真问题**

| # | 问题 | 处置 |
|---|---|---|
| 4 | **`C:` 与 `C:\` 是两回事**。`C:` 在 Windows 上是"**C 盘当前目录**下的相对路径"，而 `SystemDrive` 环境变量正好是不带反斜杠的形式 —— 测试里传 `C:` 时，那一卷被静默记成"读不到" | `bin_dir()` 补齐尾部分隔符；用例 `a_volume_without_a_trailing_separator_is_normalised` 钉住 |
| 5 | "数字不完整"原本只进审计日志，**用户看不到** | 新增 `DeleteCtx.note`：扫描层可以带一句话出来，`run_rule` 把它放进报告的 `error` 字段；前端对"状态正常但有 error"渲染成提示而不是报错 |

**新增守卫**

| 守卫 | 断言 |
|---|---|
| `the_recycle_bin_never_deletes_by_path` | `recycle_bin.rs` 里不得出现 `DeleteFileW` / `RemoveDirectoryW` / `purge_contents` / `remove_file` 一类 token；必须存在 Shell 清空调用；实测必须跳过重解析点 |

### 第 5 版（P4 实施）

P4（通用占用发现）是"通用性"这个设计目标的兑现方式，也是 P1~P4 里唯一**被实测直接改掉
设计参数**的一段。记录如下。

**实测数据推翻的两个参数**

| # | 实测 | 后果 |
|---|---|---|
| 1 | **§8.2 的"深度限制"照字面实现会给出错数字**。到第 4 层就不往下走，第 4 层目录的大小就只统计到第 4 层为止 —— 而 `%TEMP%` 在第 6 层，于是「`AppData\Local` 只占 2 GB」这种明显错误的数字会被摆到用户面前（违反 §17 验收第 14 条） | 改成：**遍历到底（统计完整），只报告浅层**。`max_depth` 是**报告深度**，不是遍历深度。代价是遍历开销上去了，由"跳过红线 + 不进入重解析点 + 低优先级 + 可取消"来控 |
| 2 | **后台 IO 优先级慢 16 倍**。同一个 `%TEMP%`（6.6 万文件 / 19 GB）：`THREAD_MODE_BACKGROUND_BEGIN` 用 **127 秒**，`THREAD_PRIORITY_BELOW_NORMAL` 用 **7.6 秒** —— 后台模式把 IO 优先级压到"仅系统空闲时"，真实负载下几乎拿不到磁盘时间片。照 §8.2 的字面要求用它，整个 C 盘要按**小时**计 | 引入 `discover::Politeness`：用户主动发起的扫描用 `BelowNormal`（确实低，但**会推进**）；无人值守的周期性扫描（P5 看门狗）用 `Background`（慢无所谓，反正没人等）。§8.2 的"标记低 IO 优先级"意图保留，量级改了 |

**真机对账（这是"数字对不对"的唯一证明）**

合成装置的用例证明不了真实目录树上的累加正确性，而"报出一个错的体积"正是这个工具最不能犯的错。
新增一条 `#[ignore]` 的手工用例 `discover_matches_robocopy`，拿 `robocopy /L /XJ`
（只列表、不跟随 junction）作为**独立基准**对账：

| 目标 | 本工具 | robocopy | 差额 |
|---|---|---|---|
| `%TEMP%`（深度 2，6.8 万文件） | 19,462,356,210 字节 | 19,462,353,980 字节 | **2,230 字节（0.00%）** |

一个坑：**robocopy 的输出是本地化的**（中文系统上是"字节"不是 `Bytes`），按标签匹配会失败 ——
改成按"含最大整数的那个数字"取（字节总数必然远大于目录数/文件数）。
跑法见用例注释。

**实现要点**

| # | 项 | 说明 |
|---|---|---|
| 3 | 排名去嵌套，**两个方向都去** | `C:\Users` 与 `C:\Users\me\AppData\Local` 会同时挤进榜单，把真正不同的发现顶掉。先按增长排（正在失控的优先），再按占用排，两榜合起来去嵌套；**相等也要去重**（两轮排序会把同一条目各推一次，榜单里出现重复行 —— 这是实施时真踩到的 bug） |

P3（回收站与隔离区）落地时，回收站这一块**实测数据推翻了方案的默认假设**，改动比预期大；

**回收站：三个实测事实改变了设计**

| # | 实测 | 后果 |
|---|---|---|
| 1 | **`SHQueryRecycleBinW` 的耗时与回收站条目数成正比**：开发机系统盘 39085 个条目 / 13.88 GB，查询耗时 **8.7 秒**；同一台机器的数据盘（58985 个目录项）**240 秒仍未返回** | §9.4 只说了"先查条目数"，没说这个查询本身可能很慢。改为**逐卷查询 + 每卷 30 秒预算**：超时的卷记为「未统计」并**显式告诉用户"上面的数字不含这些卷"**，绝不悄悄算成 0 |
| 2 | **`SHEmptyRecycleBinW` 不返回任何明细** —— 既不告诉我们删掉了哪些条目，也不给逐条进度 | I8「任何删除动作必须有审计记录」在回收站上**只能记一条汇总**。这是 Shell API 的硬限制，不是偷懒。为补偿加了两条守卫：该 API 只允许 `recycle_bin.rs` 调用；`scan.rs` 里清空调用必须出现在 dry-run 分支**之后**。另外清空**刻意不设超时** —— 放弃等待不会让 shell 停下来，反而会出现"我们报失败、文件其实正在被删"的错位 |
| 3 | 清空后的复核查询同样要走一次慢查询 | 复核失败或清空后仍有剩余时，**释放量按 0 计**并把原因写进报告（宁可少报，不可多报，与 §10.2 同一条原则） |

| 5 | §5.6 说回收站"绕过优先级 1 的保护" | 校验器为 Shell 虚拟目标**单开一条通路**：目标与策略必须严格配对（`shellRecycleBin` ⇄ `shellEmptyRecycleBin`）、不得默认勾选、`group` 必须是 `system`、不得声称可恢复。它没有文件系统路径，红线与允许根白名单都无从判定 —— 安全边界完全由「必须走 Shell API」提供 |

**`discovery_id` 提前到 P3 落地（§8.5）**

- 路径来自**系统目录对话框**，全程不经过 WebView —— 这是它能满足 I1 的前提；
- 后端签发前**走一遍闸一**，红线之内 / 非固定卷 / 被重定向的根，直接返回原因而不是签发；
- 命中用户数据 KnownFolder 的标记 `isUserData`，并要求**额外二次确认**；
- 执行隔离时**再走一遍闸一**（签发与执行之间路径可能被换成重定向）；
- id 只存在内存、不落盘，**每次任务开始即全部作废**；查不到一律拒绝，绝不回退成"把 id 当路径用"。

**实施中发现的真实缺口**

| # | 缺口 | 处置 |
|---|---|---|
| 4 | **规则模型缺一层白名单**：§5 只有 `target.kind` 与红线，于是 `fixedPath` 可以指向任何非红线目录 —— 例如 `C:\Users\me`（它既不是红线根，也不是"用户数据目录"）。规则表一旦被写坏或被篡改，就是一次全量个人数据删除 | 新增 **`purge_roots()`**：一份**封闭的、全部从 KnownFolder / 环境变量派生的**允许根清单（`%LOCALAPPDATA%`、`%APPDATA%`、`%TEMP%`、`%TMP%`、`%SystemRoot%\Temp`）。规则目标必须落在其中，否则拒绝加载。这是 I2 的落地方式：**放开新位置要显式加一条，而不是把判定放松** |
| 5 | **`C:\Users` 与用户配置文件根没人管**：它们不是红线根（否则 `%LOCALAPPDATA%` 下的缓存全清不了），也不是 §5.6 优先级 1 的"用户数据目录"，但对它们执行清空等于销毁全部个人数据 | 新增 `SafetyError::UserDataAncestor`：闸一第 4 步对"用户数据目录的严格祖先"做**精确匹配**拒绝（前缀匹配会误伤 `%LOCALAPPDATA%`） |
